# Forever Sixty in-game addon — experience spec

Author: ux-designer. References: `docs/tenets.md` (tenets 1, 2, 3, 4, 9, 11, 14 drive this
surface), `design/DESIGN-SYSTEM.md` (the palette and type scale the addon mirrors; principle 7's
crest rule and the quality-colour table), the addon as built — `addon/ForeverSixty/{Theme,
Window,Cards,Widgets,Tooltip,Toast,Tracker,TalentGlow,Minimap,Rotation,Locale}.lua`,
`addon/ForeverSixty/views/{OverviewView,FollowView,GearView,GuildView,ExportView,
SettingsView}.lua` — and the addon's own design history, binding unless it contradicts the
tenets or an owner ruling below: `docs/superpowers/specs/2026-09-20-addon-ui-design.md` §3,
`2026-09-21-addon-premium-pass-design.md`, `2026-09-28-addon-character-aware-design.md`.

There are no in-game screenshots of this addon yet (the client was installed and the addon
symlinked in today). The four boards this spec ships with are the first picture of it:
`design/mocks/renders/addon-{tooltip,overview,talents,gear}.png`, generated by
`design/mocks/gen_addon.py`, drawn at the 1.60 client's 1x UI scale on a 1920x1080 screen over a
dim vignette backdrop — never a fabricated game scene. Every name, icon, item, talent, rotation
line and number on every board is real, sourced from files already in the repo or fetched once
into `design/mocks/data/` by this lane (`addon-items.json`, `addon-talents.json`,
`addon-rotation.json`, both cut from `foreversixty.gg/data/1.60.1.70009/...`, plus the already
-present `guides-warrior-fury.json`). Anything this spec cannot source that way — a generated
sync code, a live rating card, bag contents — is specced and drawn in its real, honest empty
state, never invented (tenet 8).

**The worked character throughout:** Obnoxious Yell, a level 23 Human Fury Warrior, read against
the warrior-fury 20-29 alliance band (`guides-warrior-fury.json`'s `band: 20, faction: alliance`).
Her talent allocation at that band (`00000000000000000-353000000000000000-000000000000000000`)
puts 3 points in Booming Voice, 5 in Cruelty and 3 in Iron Will — 11 points, all in Fury; her
rotation at level 20+ (`addon-rotation.json`) is Bloodrage, Death Wish, Battle Shout, Heroic
Strike; her BiS gear is the band's own 15 sourced slots (trinkets unsourced at this band — a
real empty state, not a gap in this spec's research).

## 1. The one question, addon-wide

Tenet 14 answered for an in-game surface: every one of these seven pieces leads with Obnoxious
Yell's own build and gear, and the next thing that makes her better — never a blank panel, a
feature list, or the addon's own name as a banner. The single question changes by surface:

| Surface | The one question |
|---|---|
| Item tooltip | "Is this item better for me?" |
| Next-talent tracker | "What do I spend the next point on?" |
| Level-up toast | (the moment itself) "What did I just earn, and what do I do with it?" |
| Talent-window glow | "Which button do I press?" |
| The window | "Where do I see my whole build, my gear gaps, and send this character to the site?" |
| Minimap button / addon compartment | "Where is Forever Sixty when the window is closed?" |
| `/fs` and first run | "I just installed this — what does it want from me?" |

Tenet 11, addon-wide: one job per surface, nothing duplicated. The tooltip never shows the full
rotation; the tracker never shows gear; the window is the only place that shows the whole build.
A player who wants more than the one-line answer a surface gives opens the window — every
surface below that is not the window itself says so and links to the right page.

## 2. Design tokens: what the addon borrows from the site, and what it cannot

The addon mirrors the site's palette (`design/DESIGN-SYSTEM.md`'s Color tables) through
`Theme.HEX`, copied by hand because the addon has no CSS build to import from:

| Token | Hex | Use |
|---|---|---|
| `background` | `#0d111a` | Window body |
| `card` | `#111726` | Cards |
| `sidebar` | `#0a0e16` | Sidebar ground |
| `raised` / `hover` | `#161c2b` / `#1f2739` | Buttons at rest / under the cursor |
| `border` | `#262e40` | 1px panel and card edges |
| `titleTop` / `titleBottom` | `#131824` / `#0d111a` | Title bar, two flat stacked halves (no gradient API in this client — `Theme.gradient`'s own comment) |
| `gold` | `#e5b955` | Primary accent, active nav item, the one button style |
| `muted` | `#9a9484` | Secondary text |
| `body` | `#e9e4d8` | Primary text |
| `success` | `#6fcf8e` | Upgrade verdicts, matched/equipped notes |
| `warning` | `#ff6b5c` | Downgrade verdicts, out-of-date data |

**What does not carry over, on purpose:**

- **Typography.** The site's Cinzel/Barlow/JetBrains Mono system is a web asset the client
  cannot load. The addon uses exactly one font family, the client's own `GameFontNormal`
  (Friz Quadrata Regular) and its small/large siblings, through `Theme.FONTS`, with the shipped
  `Fonts\FRIZQT__.TTF` as the hand-built fallback when a font object is missing. **There is no
  in-game mono face** — numbers, deltas and progress counts ("7 of 11") render in the same body
  font as everything else; the site's JetBrains Mono convention does not apply here. The four
  boards stand this in with **PT Serif** (Google Fonts), the nearest widely-available face to
  Friz Quadrata's squarish humanist-serif weight at small sizes — named here as a stand-in; the
  real client renders its own Friz Quadrata at runtime and no board should be read as showing
  the final typeface.
- **Item-quality colour.** `Theme.qualityColor` reads `ITEM_QUALITY_COLORS` straight from the
  client — poor `#9d9d9d`, common `#ffffff`, uncommon `#1eff00`, rare `#0070dd`, epic `#a335ee`,
  legendary `#ff8000`. This is the client's **true, unlightened** rarity colour, not the site's
  AA-adjusted rare (`#3d94f0`) / epic (`#b866f5`) text variants the web design system specs for
  `--color-raised`. That is correct, not a divergence to fix: a player's eye for "blue item,
  purple item" is trained on the client's own colours, and the addon's own card backgrounds
  (`#111726`/`#0d111a`) are close enough in luminance to the client's default tooltip
  (near-black) that the unlightened colours stay legible. Confirmed on all four boards.
- **Crest language — owner ruling, round 2 (tenet 7, tenet 1).** The character header carries
  the circular ringed class crest (`web/public/icons/hd/crests/warrior.webp`, 36px, a 2px
  class-colour ring) to the left of the name, exactly like the site's own character rows —
  **never a square class icon anywhere in the addon.** This overturns this spec's own first-pass
  reasoning (round 1 read the crest as a web-only asset with no in-game equivalent, and the first
  wow-player review read its absence as correct); the owner's instruction stands over both. The
  name itself still carries `Theme.classColor` (`RAID_CLASS_COLORS[token]`, `#c79c6e` for
  Warrior) beside the crest — the two are not redundant, the same way the site pairs a crest with
  class-coloured text everywhere it shows one. **Implementation dependency this spec names, not
  solves:** the addon ships no web asset pipeline and no network — the crest webp cannot be
  fetched at runtime, so it must ship as bundled addon media (a pre-cropped circular texture per
  class, `ForeverSixty/media/crests/<class>.tga`-equivalent, built the same offline step that
  already produces `media/minimap.tga`), with the 2px ring drawn the same way `Theme.outline`
  already draws every other ring in this addon. A true circular crop in-frame needs `MaskTexture`
  (this client is modern enough to likely have it, same reasoning the design history gives for
  `C_Traits`/`C_Container`); guarded behind a capability check like every other client API this
  addon touches (`Theme.hasX`-shaped), falling back to a plain squared, ringed tile — never a
  blank space — on a client without it.
- **The addon's own icon** is the site's seal (`design/logo/foreversixty-mark.svg`), per
  `DESIGN-SYSTEM.md`'s Logo section ("the favicon and the addon icon are the seal alone") — used
  in the title bar, the minimap button and `Theme.MEDIA.minimapIcon`, nowhere redrawn.

`Theme.SIZES` (the addon's own pixel grid, 1x UI scale): window 720×500, sidebar 150 wide, title
bar 28 tall, header 56 tall, row height 20, card 150 tall, card gap 12, padding 16, gap 4,
tracker 240×48, toast 320×32, minimap button 32 (icon 20), minimap orbit radius 80, talent-glow
outline 2px. These are the numbers every region below is placed at.

## 3. Reference surfaces, named once

| Surface | Reference | Exactly what we borrow |
|---|---|---|
| Item tooltip | **The client's own `GameTooltip`**, never Details! or Pawn | The anatomy itself: our lines append to the *client's* tooltip, under its own name/stats/durability block, in its own unskinned black-and-gold chrome — we add text, we never draw a second panel. Pawn's convention of a single coloured verdict line is the idiom tenet 1 asks us to beat: Pawn prints a dry "Upgrade" with no source, no icon, no second tooltip. We add the icon, the quality-coloured link, the source line and a live second tooltip for the recommended item (`Theme.showCompareTooltip`) — the thing Pawn never does. |
| Next-talent tracker | **WeakAuras' own minimal text aura** | Two lines, draggable, lockable, nothing else — exactly WeakAuras' smallest unit. We add the thin progress bar WeakAuras users build by hand every time; ours ships built in. |
| Level-up toast | **Details!'s own encounter-summary popup** (brief, dismisses itself, click for more) | The "appears, says one thing, fades, click opens the detail" shape. We add the combat-lockout queue (Details! does not queue; a toast firing mid-pull is Details!'s own known annoyance) and the talent-glow tie-in. |
| Talent-window glow | **The client's own `ActionButton_ShowOverlayGlow`** (the exact call WeakAuras' "glow" trigger type uses) | The glow primitive itself. We add the mapping from a build's next point to a real button, which neither WeakAuras nor the stock talent UI does. |
| The window | **ElvUI's own config/inspect window shell** (title bar, left icon-rail navigation, content pane) at its best, never its worst (ElvUI at its worst is a thousand unlabelled checkboxes) | The icon-rail-plus-content shape. We cap it at six pages with one job each (tenet 11), where ElvUI's own panel sprawls to dozens. |
| Minimap button | **Every addon's own minimap button**, done right (DBM, WeakAuras) | Draggable ring placement, left/right click split, addon-compartment support on a client that has one. |
| `/fs` / first run | **WeakAuras' own "Import" first-run prompt** | Never a blank window — the first thing a new install shows is the one action that makes it useful (load a build), the same way WeakAuras' empty state is "import a string," not a blank list. |

## 4. Region-by-region spec

### 4.1 The item tooltip — the signature surface

**Board:** `design/mocks/renders/addon-tooltip.png` — three variants side by side at 2x scale
(the real tooltip renders at the client's small tooltip font, ~12px at 1x), plus the client's
own second tooltip for a recommended item.

**The one question:** is this item better for me — and if not, what should I get instead?

**Anatomy, top to bottom, exactly as `Tooltip.lua`'s `drawOps` builds it onto the live
`GameTooltip`:**

1. The client's own lines — name (rarity-coloured, bold), item level, slot/type, armor, stat
   lines, required level, durability — **unchanged, untouched, drawn by the client before this
   addon's hook ever runs** (`TooltipDataProcessor.AddTooltipPostCall` / `OnTooltipSetItem`,
   whichever this client has — `Tooltip.register`). The addon never reorders or recolours a
   client line.
2. One brand header: the addon's own 14px icon (`Theme.MEDIA.minimapIcon`, the seal) inline
   (`Theme.inlineIcon`) beside "Forever Sixty" in gold — one `AddLine` call, always first if
   there is anything to say at all, never drawn when there is nothing (`drawOps`'s own guard:
   `if #ops == 0 then return end`).
3. **The verdict**, coloured by meaning (`Tooltip.verdict` → `verdictFor`):
   - Something is already worn in the best-fit slot: a **percentage** of that item's own score
     — `"Upgrade +%.1f%%"` (success green) or `"Downgrade -%.1f%%"` (warning red), under
     `Tooltip.SIDEGRADE_THRESHOLD_PERCENT` (0.5%) reads `"Sidegrade"` (muted) instead of a
     coin-flip verdict.
   - Nothing is worn there: the **absolute** points fallback, `"Upgrade for %s: %+.0f by our
     weights"` (success) or `"Not an upgrade"` (muted) — there is no baseline to be a percentage
     of, so this never divides by zero.
4. **The BiS row**, one `AddDoubleLine`: left side the pick's 18px icon (`Theme.inlineIcon`,
   `Tooltip.BIS_ICON_SIZE`) plus its name as a real, quality-coloured hyperlink
   (`Tooltip.bisItemLink`); right side one tag — `"equipped"` (success, the worn item already
   matches the pick), `"new at %d"` (gold, newly best this band), or the default `"BiS · lvl
   %d"` (muted). Then, when known, the pick's item level (`"Item Level %d"`, muted) and its
   source line (`"<kind> · <place>"`, e.g. `"Crafted · Blacksmithing"` or `"Dungeon · Wailing
   Caverns · Mutanus the Devourer"`, muted) — **never a bare `"Source: Crafted"`**: a pick with
   no place label gets no source line at all rather than the kind alone.

   **Build requirement, exact (round-2 must-fix, no longer a proposed ruling — §10.1 is
   adopted):** the BiS row draws for **any item whose equip location maps to a slot the band
   tracks** (`Gear.SLOTS_BY_EQUIP_LOCATION`), not only when `Tooltip.equippedSlotFor` finds a
   byte-exact match to what is currently worn. Today's shipped `Tooltip.sections` only calls
   `Tooltip.bisLines` on that exact-worn-item path; the fix removes that precondition so the
   verdict and the pick row draw together on **every** hover that lands in a tracked slot —
   a bag item being compared, an empty character-pane slot, the worn piece itself, all the same
   one code path. This is the one thing Pawn always does (any item, any slot, instant verdict +
   "get this instead") that this addon does not yet; it is the single biggest gap against tenet
   1 on this surface and must land before an in-game build can be called a match for this spec.
5. Cap call-outs, when the companion's inbox carries a `weights` message with `caps` for this
   spec: `"%s capped: more is wasted"` per capped stat the item carries, in body text.

**No equip affordance in the tooltip, by design.** Hovering is for deciding, not committing;
Equip lives on the Gear page's own row (§4.5.3), the one place a click there has a combat-lockout
guard and an enabled/disabled state to show. A tooltip verdict is read-only everywhere.

**The three variants on the board, every one real data against Obnoxious Yell's own band:**

- **BETTER** — hovering `Veteran's Silvered Chain Helm` (`item_id` 250528) for an **empty** head
  slot: `"Upgrade for head: +20 by our weights"` (the absolute branch — nothing worn, score 20.09
  from `strength 10 × 2.0090`), BiS row tagged `"BiS · lvl 20"`, source `"Crafted ·
  Blacksmithing"`.
- **WORSE** — hovering `Veteran's Chain Shirt` (an alternative, `item_id` 250488) while
  `Mutant Scale Breastplate` (the real BiS pick, already worn) sits in the chest slot:
  `"Downgrade -28.1%"` (percentage branch — alt scores 14.45 against the worn piece's 20.09), BiS
  row tagged `"equipped"` in success green (confirming the pick is already on), source
  `"Dungeon · Wailing Caverns · Mutanus the Devourer"`.
- **UNRATED** — hovering `Rune of Perfection` for trinket1, which has **no sourced pick at this
  band** (`empty_reason: "no_sourced_item"`, real data): `"Not an upgrade"` only (the item's own
  stamina/spell-penetration score under these weights, both zero-weighted) — **no BiS row at
  all**, because `Tooltip.bisLines` finds no entry for this slot and correctly says nothing it
  cannot back up, rather than guessing. This is tenet 7's "never a dump," applied to silence: the
  addon's quiet is itself the honest answer.

**Two states this spec names but does not render a fourth/fifth panel for (board space; named in
full here instead):**

- **Equal (sidegrade)** — hovering the exact item already worn in its own slot: `equippedScore`
  equals the hovered item's score, delta 0, reads `"Sidegrade"` muted; the BiS row (drawn because
  the slot is tracked, same rule as every other case now) shows `"equipped"` if it's also the
  pick, or the plain `"BiS · lvl %d"` tag if a better pick exists elsewhere — telling the player
  what they wear is fine but not best, without a loud downgrade verdict for something they cannot
  change mid-dungeon.
- **For a different class / unmapped slot** — an item whose `INVTYPE` has no entry in
  `Gear.SLOTS_BY_EQUIP_LOCATION` (a shirt, a tabard, a bag, ammo) draws **nothing at all**:
  `Tooltip.verdict` returns `nil`, no brand header shows, the tooltip is the client's own,
  unmarked. This is correct and matches `Tooltip.BIS_SLOT_BUTTONS`'s own exclusion of Shirt and
  Tabard from the empty-slot hover — never a guess at a slot this character cannot meaningfully
  fill.

**States, full matrix:** default (nothing shown, `Prefs.flag("tooltip")` off, or the item hook
disabled itself after a prior error — `Tooltip.disabled`), loading (item not yet cached —
`Tooltip.onItemInfoReceived` redraws in place the moment `GET_ITEM_INFO_RECEIVED` confirms it,
no flash of missing data because the verdict only draws once stats are known), the five content
states above, error (a hook failure disables itself silently rather than breaking every tooltip
in the game — found in game twice per the file's own comment, `pcall`-guarded).

**Polish limits:** no second frame — everything here is text appended to the client's own
`GameTooltip`/compare tooltip, never a themed panel; no frame-strata fight (the compare tooltip
sits at `"TOOLTIP"` strata, anchored off `GameTooltip`'s own right edge, and hides the instant
`GameTooltip` does, hooked once); no taint — the tooltip hook never touches a protected frame or
calls a protected function; a Lua error inside the hook turns the hook off rather than breaking
every tooltip in the game for the rest of the session.

**Acceptance screenshots:** in-game, 1x and 1.15 UI scale, 1920×1080 — (a) the BETTER variant
over an empty paperdoll slot (the empty-slot hover path, `Tooltip.onSlotEnter`), (b) the BETTER
variant over a bag item (the item-hook path), (c) the WORSE variant with the compare tooltip
visible beside it, (d) the UNRATED variant confirming no BiS row draws, (e) the equal/sidegrade
state on the character's own worn gear, (f) an unmapped-slot item (a shirt) confirming no brand
header shows at all, (g) the tooltip toggle off in Settings confirming nothing draws.

### 4.2 The next-talent tracker

**Board:** `design/mocks/renders/addon-overview.png` (top-centre, in its real default screen
position).

**The one question:** what do I spend the next point on?

**Layout, 240×48 (`Theme.SIZES.trackerWidth/trackerHeight`), `Widgets.panel` chrome (`#111726`
body — actually the panel background key, `#0d111a`-family — 1px `#262e40` border):** title line
(gold, small font, `Tracker.title`) — `"Next: <build-line>"`, where `<build-line>` is
`Follow.line`'s own `"<talent> (<tree>, tier <n>)"`; progress line (muted, small) — `"<spent> of
<total>"`; a 4px-thick gold fill over a `#1b2233` track, width `trackerWidth - gap*2` (232px),
directly under the progress line. For Obnoxious Yell: `"Next: Booming Voice (Fury, tier 1)"` /
`"7 of 11"` / a bar at 64%.

**Default on-screen position:** `Prefs.DEFAULTS.tracker` — anchor `TOP`, `x=0, y=-180` — centred
horizontally, 180px below the top of the screen. Draggable (`StartMoving`/`StopMovingOrSizing`,
position saved) unless locked (`Prefs` `tracker.locked`); clamped to screen.

**States:**

| State | What shows |
|---|---|
| No build loaded | Hidden entirely (`Tracker.model`'s own `shown = false`) |
| Build loaded, points remaining | The two lines and bar above |
| Build complete | Title `"Build complete"`, bar full, progress `"<total> of <total>"`, then auto-hides after `Theme.SIZES.completeSeconds` (5s) — or stays up forever on a client with no `C_Timer`, since a stuck "Build complete" is a lesser lie than a player who can never see their build finished |
| Toggled off in Settings | Hidden, `Prefs.tracker.shown = false` |
| Locked | Same draw; drag is a no-op (`OnDragStart` checks `locked` before `StartMoving`) |
| Unlocked, dragging | Follows the cursor; `OnDragStop` saves the new point/x/y |

**Copy, verbatim:** `trackerNext = "Next: %s"`, `trackerProgress = "%d of %d"`, `trackerComplete
= "Build complete"`.

**Polish limits:** no frame-strata fight with the window or the toast (default strata, sits
above game world UI the same as any movable addon frame); keyboard never captured (no edit box,
no focus target at all); drag only on left-button, never interferes with camera drag.

**Acceptance screenshots:** 1x and 1.15 scale — the four visible states above, plus a drag-in-
progress frame and the locked state's cursor-has-no-effect frame.

### 4.3 The level-up toast

**Board:** `design/mocks/renders/addon-talents.png` (top-centre).

**The one question (the moment itself):** what did I just earn, and what do I do with it?

**Layout, 320×32 (`Theme.SIZES`), same `Widgets.panel` chrome as the tracker, text centred, gold,
small font.** Anchored `TOP`, `y = -80` (`Toast.TOP_OFFSET`) — above the tracker's own 180px
offset, never overlapping it in the default layout.

**Trigger and copy, exactly:** `PLAYER_LEVEL_UP` always fires the talent-point half
(`toastMessage = "Level %d. Take %s, rank %d of %d."`); a confirmed rise in unspent talent points
(when the client's trait API answers the question at all — `Toast.unspentPoints`) fires the
rotation half independently (`rotationToastMessage = "Level %d: %s opens your rotation now."`);
**both share one frame and one fade timer** — a level-up that triggers both shows one combined
message (`Toast.combined`, joined by two spaces), never two popups racing each other. For
Obnoxious Yell crossing into rank 3 of Booming Voice: `"Level 23. Take Booming Voice, rank 3 of
3."` — no rotation half fires here, because levels 20-29 share one rotation band
(`addon-rotation.json`: level 20's four lines are identical in name to level 10's; `Rotation.
newAbilities` compares by name, not rank, so no line reads as "new").

**States:** hidden (no build loaded, or `Prefs.flag("toast")` off); shown (5s fade,
`Toast.FADE_SECONDS`); **held, not skipped, in combat** — `Theme.inCombat()` queues the model
rather than dropping it, and flushes it (`Toast.flushPending`) the moment combat ends, so a
level-up mid-pull is never silently lost; click anywhere on the toast opens the Talents page
(`Window.open("follow")`).

**Copy table:** see §6.

**Polish limits:** never shows mid-combat (protected-action safety, not just politeness — a
frame appearing and stealing focus during a boss fight is the kind of thing that gets an addon
blamed for a wipe); no keyboard capture (click-only, no edit box); one frame reused every time,
never a stack of toasts.

**Acceptance screenshots:** the combined-message state, the talent-only state, the rotation-only
state (crossing a real new-ability rung, e.g. level 30 adding Execute), the held-in-combat state
(toast absent while `InCombatLockdown()` is true) and its flush the instant combat ends.

### 4.4 The talent-window glow

**Board:** `design/mocks/renders/addon-talents.png` (right side, labelled fragment — never the
whole talent frame, per the owner's no-fabricated-scene instruction).

**The one question:** which button do I press?

**What it is:** a 2px gold ring (`Theme.outline`, the texture fallback) or the client's own
`ActionButton_ShowOverlayGlow` pulse (whichever this client has — `hasOverlayGlow`'s own
once-per-session probe) on the next point's button, found by trying, in order, the classic
`TalentFrameTalent<n>` naming (scoped to the tab the frame reports open — a glow on the wrong
tree is worse than no glow, so an unknown open tab is never guessed) and a walk of the modern
trait frame's children for a `nodeID` match (`TalentGlow.traitButton`, 3 levels deep). For
Obnoxious Yell the next point is Booming Voice (tier 0, column 1) — the board's fragment rings
exactly that tile.

**States:** no glow (no build, or the talent window is closed — `TalentGlow.openFrame` finds
nothing shown); glowing (above); glow present but addon cannot map it to a real button on this
client (`diagNoTalentButton`, recorded once to `/fs diag`, never a Lua error) — the tracker still
works regardless, since the glow is a bonus, not the only way to know the next point.

**Polish limits:** never taints the talent frame — the addon only reads (`GetChildren`,
`nodeID`) and calls the client's own show/hide glow functions, never sets a protected field;
cleared (`TalentGlow.clear`) the instant the window closes or the build finishes, never a stray
ring left on a button after the fact.

**Acceptance screenshots:** the talent window open with the glow on the real next-point button
(both the classic-naming and trait-node-walk paths, if this client's talent UI uses the modern
trait system — record which mapping fired, same as the addon's own README spike table).

### 4.5 The window

**Boards:** `addon-overview.png`, `addon-talents.png`, `addon-gear.png` (Guild, Export, Settings
pages are specced below from `GuildView.lua`/`ExportView.lua`/`SettingsView.lua` directly; no

**The one question:** where do I see my whole build, my gear gaps, and send this character to
the site?

#### 4.5.1 Chrome

- **Title bar**, 720×28, two flat stacked halves (`#131824` top, `#0d111a` bottom — no gradient
  API on this client, `Theme.gradient`'s own comment): the seal (16px) + `"Forever Sixty"` gold,

- **Sidebar**, 150 wide, `#0a0e16` ground, 1px right border: six items, 30px tall each, 8px below
  the title bar — Overview, Talents, Gear, Guild, Export, Settings, each a 16px icon
  (`Theme.NAV_ICONS`: `INV_Misc_Map_01`, `INV_Misc_Book_09`, `INV_Chest_Chain`,
  `INV_BannerPVP_02`, `INV_Letter_15`, `INV_Misc_Gear_01` — real client icons, boards fetched
  the same slugs) plus a label. The active item: a 2px gold bar down its left edge, a raised

### 4.6 Minimap button and the addon compartment

**Board:** `design/mocks/renders/addon-overview.png` (top-right, in its real on-screen position).

## 7. There is no phone/desktop split; there is 1x and 1.15 UI scale

This surface has no responsive concept — the client is the client, and the addon's job is to
look right at whatever `uiScale` the player has set, not to reflow for a viewport. The owner's
own instruction stands in place of a phone/desktop split: **every acceptance screenshot in this
spec is captured twice, once at the client's 1x UI scale and once at 1.15x**, on a 1920×1080
screen. What must never change between the two: every row's `Theme.SIZES.rowHeight` (20px) stays
proportional (WoW's `uiScale` multiplies the whole frame, not individual elements, so this is a
property of the client, not something this addon can get wrong on its own); what must be checked
by eye at 1.15x specifically: the window (864×600 at that scale) still clears the screen with
`SetClampedToScreen(true)`, and no card's text wraps somewhere it did not at 1x (`Cards.card`'s
fixed-width title/detail regions are sized off `contentWidth`, itself derived from
`windowWidth`, so they scale together — this is a thing to verify in game, not assume from the
boards, which are drawn at one notional scale).

## 8. Performance and polish limits, addon-wide

- **No frame-strata fights.** Window `DIALOG`, tracker and toast default strata, minimap button
  `MEDIUM`, compare tooltip `TOOLTIP` (anchored off `GameTooltip`, hides with it). Nothing in
  this addon ever sets a strata above `TOOLTIP` or fights the client's own action bars.
- **No taint.** Every protected call (`EquipItemByName`/`C_Item.EquipItemByName`) runs only from
  a direct player click, never from an event handler or a timer; `InCombatLockdown()` is checked
  both at render time (button disabled) and again inside the click handler itself (the file's
  own comment: a render-time check alone would leave a stale-enabled button able to equip if
  combat started while the tab sat open).
- **No keyboard capture after close.** Every edit box releases focus on hide (`Widgets.
  releaseFocusWhenDone`) — the exact in-game defect this mechanism was built to fix (opening the
  window once left every keybind dead until Escape).
- **No missing-icon flash.** Every icon draws the neutral tile (`Theme.UNKNOWN_ICON`) immediately
  if the texture is not yet known, never a blank square, and redraws in place the instant the
  client's item cache answers (`Tooltip.onItemInfoReceived`) — never a second draw pass the
  player has to notice.
- **No frame created at load.** Window, tracker, minimap button and the compare tooltip are all
  built on first need (`Window.ensure`, `Tracker.ensure`, `MinimapButton.ensure`, `Theme.
  compareTooltip`) — `Options.register()` at file load only registers events and the slash
  command, per the addon's own architecture rule.
- **One Lua error never breaks every tooltip in the game.** Every tooltip hook body runs inside
  `pcall`; a failure disables that hook for the rest of the session and records one diagnostic
  line, rather than raising a second time on the very next hover (`Tooltip.onTooltip`'s own
  comment: this happened twice before the guard existed).
- **No network, ever.** Every fact on every surface in this spec comes from `Data.lua`
  (generated), the companion's `ForeverSixtyInbox` (private, per account), or something the
  player pasted. A design question this spec could not answer from one of those three is named
  as an honest empty state, never guessed.

## 10. Rulings proposed for the owner

Seven findings from reading the shipped `Tooltip.lua`/`OverviewView.lua`/`FollowView.lua`/
`GearView.lua` against tenet 1's own standard, plus one named implementation dependency (ruling 7), each with the fix this spec's boards already draw.
None of these are hypothetical: each is a specific line of code read during this pass. **Ruling 1
is adopted, not proposed** — round 2 of this lane's review (`design/reviews/
2026-10-04-addon-mock-wow-player.md`, finding 3) confirmed it as the single biggest gap against
Pawn on the signature surface and the coordinator made it a build requirement; §4.1's own anatomy
section now states the exact hook rule directly rather than only here. Rulings 2-5 remain
proposed, pending owner sign-off and a code change — the boards draw the fixed behaviour in every
case, which is not the same as the build matching it yet (the first-round review's own finding 6,
still true).

1. **Adopted: the BiS row draws on any item occupying a tracked slot, not only the exact-equipped
   link.** Today, `Tooltip.sections` only calls `Tooltip.bisLines` when `Tooltip.
   equippedSlotFor(itemLink)` finds a byte-exact match to what is currently worn — meaning a bag
   item the player is actually comparing gets the verdict line but **never** the recommended
   pick, its icon, or its source, unless the player backs out and hovers the empty character-
   pane slot instead. This is the single biggest gap against tenet 1 on this surface: Pawn
   already shows a verdict; what beats Pawn is showing the player what to get instead, every
   time, not only when they happen to already be wearing the right thing. **Fix, exact (§4.1):**
   extend the item hook to also draw the BiS row whenever the hovered item's equip location maps
   to a tracked slot (`Gear.SLOTS_BY_EQUIP_LOCATION`), regardless of whether it is the exact worn
   item. The tooltip board (§4.1) draws the target, fixed behaviour throughout.
2. **The Overview's arrival-banner region never collapses.** `OverviewView.layout`'s `gridTop`
   constant always reserves `BANNER_HEIGHT + cardGap` (84px), whether or not there is a pending
   build to show — a dead gap above the card grid on the common case. **Fix:** collapse that
   reservation to zero when `model.arrival.visible` is false. The overview board (§4.5.2) renders
   the fixed layout.
3. **The build-name fallback is not title-cased.** `followBuildName = "%s build"` formats
   straight off `build.classSlug` (`"warrior"`), giving `"warrior build"` — lowercase, ungroomed
   — when no build name was saved, while `Window.specLabel` right there in the same codebase
   already solves exactly this problem for the spec label (`"warrior-fury"` → `"Fury"`). **Fix:**
   title-case the class segment the same way before formatting. The board shows `"Warrior
   build"`.
4. **The tier number shown to players is 0-indexed.** `Follow.line`'s `followNext` format passes
   `point.tier` straight through from `Data.lua`'s own zero-based tiers, so the tracker, the
   toast and the Talents page all print `"tier 0"` for the first row — while the real talent
   window the player can see right next to it labels its rows Tier 1 through 8. **Fix:** add 1
   wherever `point.tier` is formatted for a player (not in the data itself, which stays
   zero-based for every internal lookup). The boards show `"tier 1"`.
5. **`GearView`'s own "Upgrades in your bags" section has no empty-state copy.** When `model.
   upgrades` is empty, the page draws the `"UPGRADES IN YOUR BAGS"` header and nothing under it
   — `L.gearNone = "Nothing in your bags beats what you are wearing."` already exists in
   `Locale.lua`, already the right sentence (it is literally what the Overview's own Gear card
   shows for the identical state), and is simply never referenced in `GearView.lua`. **Fix:**
   wire it into `GearView.apply` under the header when the list is empty. The gear board (§4.5.4)
   shows the fixed state.
6. **Adopted (round-2 must-fix): `GearView`'s item cells must carry a real hyperlink with the
   client's own hover tooltip.** Tenet 2 is unconditional — *wherever* an item appears, hover
   shows the real tooltip — and the main item-hook surface (§4.1) and the Talents page's own BiS
   row both already do this; `GearView.lua`'s Planned/Equipped columns must too, or they are the
   one place on the addon where an item is "just a name." **Fix:** every `GearView` row calls
   `GameTooltip:SetHyperlink` (an item already cached) or `SetItemByID` (one this character has
   never seen) on `OnEnter`, the same `Widgets.attachTooltip` helper `Widgets.itemRow` already
   uses elsewhere in this file — not a new mechanism, just applying the existing one to every
   Planned/Equipped cell. The gear board (§4.5.4) renders every item name as an underlined,
   quality-coloured link and shows one hover-tooltip capture to make the requirement explicit.
7. **Named implementation dependency, not a code-reading finding: the class crest needs bundled
   media.** The owner's round-2 ruling (§2, §4.5.1) puts the circular ringed crest in the
   character header; the addon has no network and no web asset pipeline, so the crest texture
   must ship as addon media (one pre-cropped circular file per class, built offline the same way
   `media/minimap.tga` already is) with the ring drawn by the addon's own `Theme.outline`, and a
   `MaskTexture` capability check (guarded like every other client API this addon touches) for
   the circular crop itself, falling back to a plain squared, ringed tile rather than nothing on
   a client without it.
