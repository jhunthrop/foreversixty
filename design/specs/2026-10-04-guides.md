Author: ux-designer. References: `docs/tenets.md` (14 tenets, tenet 14 "player helper, not a
reference site" and tenet 11 "hierarchy over density" above all), `design/DESIGN-SYSTEM.md`
(principle 3 — no source pills in a header; the Class page header family, Stat weights rail,

`web/src/components/{ArtPanel,ClassHeader}.astro`, `web/src/components/bis/{ThisSetPanel,
StatWeightsPanel,PlayItPanel}.astro`) as the sibling page this rebuild must feel like one site
with, the live pages this replaces (`web/src/pages/guides/index.astro`, `web/src/pages/guides/
[class]/index.astro`, `web/src/pages/guides/[class]/[spec].astro`, `web/src/layouts/
Content.astro`), the components already shipped for this surface (`web/src/components/guides/
{BuildActionButtons,GuideBuildTree,RacePillRow,StatPriorityPills}.astro`, `web/src/components/

Three surfaces, one job each, climbing in specificity: `/guides` picks the class, `/guides/
<class>` picks the spec, `/guides/<class>/<spec>` teaches the spec. Every pixel size, colour
and copy string below is quoted verbatim from the design system, computed from a real data
file with its source named, or cited as an existing component the build lane must reuse, never
invent (tenet 10).

## 1. Purpose and the one sentence

### 1.A `/guides` — pick your class

Tenet 14's front door, read literally: this is one of the two pages a signed-out visitor is
sent to from the home hero's nine-crest picker (`web/src/pages/index.astro` already links
every crest to `/guides/${slug}`), so it is also effectively the class-picker's own landing
page, not a reference index of thirty-six articles.

| Entry | The one question | What answers it |
|---|---|---|
| Signed out, or signed in with no character | "Which class am I reading about?" | Nine crests, one screen, no scroll to the ninth (§4.A). |
| Signed in with a character | "Where's my own guide?" | A one-line callout above the grid naming the visitor's own class and spec guide by name, the exact phrasing the BiS page's own `classGuideLink` convention already uses for this hand-off (§4.A). |

**Must be visible with no scrolling**, 360px phone / 1280px desktop:

| | 360px phone | 1280px desktop |
|---|---|---|
| Must show | Eyebrow, h1, the signed-in callout line (if signed in), at minimum the first three class crests of the grid | Eyebrow, h1, the signed-in callout line (if signed in), all nine crests |

### 1.B `/guides/<class>` — pick your spec

| Entry | The one question | What answers it |
|---|---|---|
| Any visitor | "Which of this class's three specs do I play, and why?" | Crest, one identity paragraph, three spec cards each naming its role and its one differentiating line (§4.B). |
| Signed in on this class | "Is this already my spec?" | The matching spec card carries a small "Your spec" tag, the same quiet convention `ClassHeader`'s active-tab ring already uses elsewhere, never a second headline. |

**Must be visible with no scrolling**, 360px phone / 1280px desktop:

| | 360px phone | 1280px desktop |
|---|---|---|
| Must show | Crest, h1, first spec card in full (icon, role, line, button) | Crest, h1, identity paragraph's first two lines, all three spec cards in full |

### 1.C `/guides/<class>/<spec>` — how to play it

| Entry | The one question | What answers it |
|---|---|---|
| Any visitor | "What do I actually do with this spec, right now?" | The header names the spec; immediately under it, a 3-up rail answers Build / Rotation / Stat priority without reading a word of prose (§4.C). |
| A visitor who already has the build loaded or simmed | "What's the reasoning behind it?" | The prose sections below the rail, in a fixed order, a sticky "On this page" jump list beside them (kept, `SpecTableOfContents`). |
| A visitor leveling this spec right now | "What do I respec into at the next bracket?" | The Leveling section's band strip: one row per band, a real sim-checked talent string and a direct planner link, never a single truncated level-60 string standing in for five brackets (§4.D, the first proposed ruling, §10). |

**Must be visible with no scrolling**, 360px phone / 1280px desktop:

| | 360px phone | 1280px desktop |
|---|---|---|
| Must show | Eyebrow, h1, Updated stamp, the Build card's header + Load/Sim buttons (rest of the 3-up rail is the next scroll) | Eyebrow, h1, Updated stamp, description sentence, and all three rail cards (Build, Rotation's first 4 lines, Stat priority pills) in one row |

The phone figure is the narrowest the site designs for (`web/lighthouserc.json`'s own mobile
emulation width, 360px). What does not fit is the next region down, never a second copy of
what is already on screen (tenet 11).

## 2. Reference

- **Wowhead's class-overview → spec-guide drill-down.** Wowhead's own class hub page is
  exactly a crest grid into three spec pages, which is what `/guides` now borrows for its
  layout (§4.A) — what we do differently (and better, per tenet 1): every crest is the real
  HD ringed crest in the class's own colour (tenet 7), never a flat Wowhead-style icon tile,
  and a signed-in visitor gets her own spec named above the grid instead of Wowhead's
  anonymous "pick a class" with no notion of who is asking.
- **Icy Veins' spec-guide anatomy** (gearing summary box → talent tree screenshot → rotation
  priority list → stat priority → consumables, with a sticky in-page nav) is the shape
  `/guides/<class>/<spec>` already follows one-for-one (`SPEC_SECTIONS`, kept unchanged) and
  what this rebuild keeps verbatim. What we do differently: Icy Veins' gearing box is static
  prose with no interactive tree; ours is the real, loadable talent tree (`GuideBuildTree`,
  kept) plus the "Load this build"/"Sim this build" hand-off Icy Veins has no equivalent of at
  all — tenet 14's own differentiator, now surfaced above the fold instead of two screens down
  (§4.C's 3-up rail is the fix: the BiS page's own review already named this exact pattern as
  the site's edge over a pure reference site).
- **The in-game talent pane's own tree.** `GuideBuildTree` (kept, unchanged mechanism) already
  renders the planner's own `TreeGrid` read-only — the same three-column, tier-and-column grid
  a player's own in-game talent frame uses, not a screenshot or a static image the way Icy
  Veins ships it. This rebuild's only change to that component is where it sits (inside the
  new Build rail card, §4.C) and shrinking it to a thumbnail at rest.
- **The BiS page's own Class page header family** (`ArtPanel` + `ClassHeader`,
  `design/DESIGN-SYSTEM.md`'s "Class page header") is the header this rebuild reuses for the
  spec guide (§4.C) and, pared to its `minimal` mode, for the class landing (§4.B) — so a
  visitor moving between `/bis/warrior/fury` and `/guides/warrior/fury` sees the identical
  crest, h1 treatment and `SpecTabs` row, never two different header languages for the same
  class and spec (tenet 10).

## 3. What this rebuild keeps and what it replaces

**Kept, unchanged mechanism (restyled chrome only where the header wraps it):**
- `GuideBuildTree.svelte`, `BuildActionButtons.astro`, `RacePillRow.astro`,
  `StatPriorityPills.astro`, `SpecTableOfContents.astro` and the section-splitting pipeline
  (`lib/guides/{sections,markdown}.ts`) — every one of these already does its job correctly;
  this spec only repositions `GuideBuildTree`/`BuildActionButtons` into the new rail (§4.C)
  and leaves the other three exactly where `[spec].astro` already plants them.
- `Content.astro`'s own article/aside grid, `SourcesList`, `UpdatedStamp`,
  `confidencePlacement="footer"` — all kept; the spec guide's header moves out of
  `Content.astro`'s own plain `<h1>` into the new `ArtPanel`+`ClassHeader` region (§4.C), but
  the prose column, the sticky aside and the Sources footer underneath are unchanged.
- All thirty-six content files (`web/src/content/guides/**/*.md`) — zero frontmatter or prose
  changes; this is a layout rebuild, not a content rewrite. The Leveling band strip (§4.D)
  reads the existing public BiS file for the matching spec, not a new frontmatter field.
- `racePillsFor`/`RacePillRow`'s own documented ruling that race art does not exist yet (its
  own header comment already states this) — carried forward unchanged, confirmed again as
  this spec's own ruling in §10 rather than silently relied on.

**Replaced:**
- `/guides`'s `ClassTile` + flat text-link rows (`web/src/pages/guides/index.astro`'s current
  `<section>` list, confirmed by screenshot `guides-index-1440.png`) → the nine-crest grid
  (§4.A) — the single clearest "plain list where a panel was expected" defect on the site
  today (tenet 1), and the only index page left that still looks like a sitemap rather than a
  tool.
- `/guides/<class>`'s bare two-link paragraph plus a plain `<ul>` of spec names
  (`web/src/pages/guides/[class]/index.astro`, confirmed by `guides-hunter-1440.png`) → crest
  + identity paragraph + three illustrated spec cards (§4.B).
- `/guides/<class>/<spec>`'s plain `<h1>` title with no class identity at all (confirmed by
  `guides-warrior-fury-1440.png` — a reader cannot tell this is a Warrior page without reading
  the words) → the full `ArtPanel`+`ClassHeader` band, matching `/bis` (§4.C).
- The Leveling section's single paragraph of prose with no concrete talent data
  (`fury.md`'s own closing section today is pure prose) → the band strip, pulling the same
  verified per-band talent strings the BiS page's own band tabs already use (§4.D, proposed
  ruling §10.1).
- The 3,800px unbroken scroll from title to Sources with nothing answering "what do I do"
  before the first prose paragraph (tenet 14's own complaint about this exact page) → the 3-up
  rail directly under the header (§4.C), so the hand-off tenet 14 asks every page to lead with
  is answered before any prose loads.

## 4. Region-by-region spec

Design tokens cited are from `design/DESIGN-SYSTEM.md` unless noted. Page gutter 48px desktop
/ 18px phone, content max width 1344px (the header band); the prose article column stays
`Content.astro`'s own 820px, capped for readability at 68ch for running text specifically
(§4.D's own note — the first place this site states a `ch` limit, not just a pixel column).

### 4.A `/guides` index — new, `GuidesClassPicker.astro`

**Why not reuse the home page's own nine-class row verbatim:** the home hero's picker
(`index.astro`'s `home-class-picker`) is a 56px crest with a name underneath and nothing else
— correct for a hero sidebar, too thin for a page whose entire job is this one grid. This
page's own grid is larger (84px crest) and carries the three spec names under each class, the
one piece of information the home picker intentionally omits (tenet 11: the home picker is
secondary to the hero's headline; here the grid *is* the page).

- **Shows:** eyebrow, h1, the "Updated" stamp, the honesty line (kept, shortened), the
  signed-in callout (signed in only), a 3-column (desktop) / 1-column (phone, horizontally
  unscrolled — a real grid, not a carousel) grid of nine class cards.
- **Class card, each:** `ClassCrest` at 56px (not 84 — nine of them at 84px with three spec
  links each overflows 1280px without scrolling the grid itself; 56px matches the home hero's
  own crest size exactly, tenet 10's "reuse the token" discipline, confirmed against
  `ClassCrestSize = 36 | 44 | 56 | 64 | 84`), the class name in the class colour (Cinzel 14px
  700, the exact `home-class-picker` treatment), then the three spec names as plain text links
  underneath, 13px, stacked, `text-nav`. The whole card sits in a `panel` box
  (`bg-raised`/`border-line`, `radius-panel` 6px) — never a bare crest floating with no card
  boundary, so nine of them read as a grid of tiles, not a loose row of icons (tenet 1: a list
  where a panel was expected).
- **Grid:** `grid-cols-3` desktop (three rows of three, matching the home hero's large-picker
  convention `grid-cols-3 gap-[10px] sm:grid-cols-9` — here kept at 3 columns even at desktop
  width, since each card is taller with its three spec links, unlike the home hero's flat
  9-across crest-only row), `grid-cols-1` phone (nine full-width rows, each 44px+ tall and
  immediately scannable top to bottom, no horizontal scroll — a sitemap of nine items is
  exactly the case `Hierarchy over density` tolerates full vertical scroll for, since every row
  is already single-purpose).
- **Signed-in callout**, above the grid, only when `me.characters[0]` resolves: one line,
  `ClassCrest` at 36px, class colour, linking straight to that character's own spec guide
  (§6's copy table). This is the literal front door tenet 14 describes ("leads with the
  player's class or character") — the grid below still works for every other class the visitor
  might want to read, but the first thing a signed-in visitor sees is her own.
- **State:** `Skeleton` (one line, 36px crest + text) for the callout while `/v1/me` resolves;
  omitted entirely on failure or signed-out (the grid underneath needs nothing from this fetch
  and never waits on it — same "deferred, never blocking" discipline the logs hero's own hook
  line uses).

### 4.B `/guides/<class>` class landing — `ArtPanel` + `ClassHeader` (`minimal`) + new spec cards

- **Header:** `ArtPanel` wrapping `ClassHeader` in its existing `minimal` mode (crest 64px,
  h1 `{className} in Forever` in the class colour, `SpecTabs` row — no band/faction suffix, no
  summary sentence, no controls row, exactly the mode the component already ships for a
  healer/tank spec with no ranked BiS). `SpecTabs` here link to this class's own three spec
  guides (`/guides/<class>/<spec>`), not `/bis/...` — same component, different `href`s, the
  prop already supports this (`SpecTabEntry.href`).
- **Identity paragraph:** the content file's own first paragraph (`index.md`'s body, e.g.
  Warrior's "Warrior is Forever's pure melee class...") — unchanged prose, rendered at the
  existing `prose-forever` scale, capped 68ch (§4.D's own rule, since this is also running
  text). The rest of `index.md`'s body (the specs list, the race/pairing paragraph, the
  patch-notes paragraph) renders below the spec cards, unchanged order and content — the cards
  are additive, not a replacement for the prose a visitor who keeps reading still gets.
- **Spec cards**, a `grid-cols-3` row (desktop) / stacked column (phone) directly under the
  identity paragraph, one per spec, in tree order (`position` ascending, the same order
  `SpecTabs` already uses):
  - Spec icon 40px (the same per-tree first-talent icon `specTabIcon` already resolves for
    `SpecTabs`, reused here at a larger size — one source of truth for "the icon that
    represents this spec", never a second lookup).
  - Role label, 11px uppercase `label` token, from the guide's own `role` frontmatter (`dps` →
    "DPS", `tank` → "Tank", `healer` → "Healer").
  - One line: the guide's own `description` frontmatter field, already written as a single
    sentence for exactly this kind of summary use (confirmed: every spec guide's
    `description` is one sentence, e.g. fury's "Talents, rotation, stat priority, and race
    picks for Fury Warrior in Forever, with beta-versus-projection called out." — trimmed in
    this card to its own natural clause break if over ~90 characters; the build lane's own
    judgement call, never a hard CSS clamp on a sentence tenet 4 protects).
  - Set DPS, mono, **only when the spec's own band-60 BiS file resolves a `set_dps`** (fury and
    arms both do — `data/builds/1.60.1.70009/bis/warrior-{fury,arms}.json`'s own last band;
    protection has no ranked file, the same `file === null` case `/bis`'s own page already
    renders an empty state for, so its card simply omits this line — never a zero or a dash
    standing in for missing data, tenet 8). **Faction, exact rule (round-1 mock review finding
    1, closing a gap this section left open): the guide's own first `recommendedRaces` entry
    decides which faction's band-60 row to read — the identical rule §4.D's Leveling band strip
    already states, now stated here too so the two figures on the site (this card's DPS and the
    Leveling strip's own talent data) can never read from two different factions by omission.
    Fury's own `recommendedRaces: [human, troll]` → human → Alliance → 262.0 DPS; Arms's own
    `[human, orc]` → human → Alliance → 201.6 DPS — never the Horde band, and never a number
    typed into the build lane's own code (the mock generator's own round-1 defect: it had
    `SPEC_SET_DPS = {'Arms': 195.1, 'Fury': 241.5}` hardcoded, the Horde figures, silently
    contradicting this very rule).**
  - Button: `Read the guide` → `/guides/<class>/<spec>`, Secondary button token.
  - Signed-in match: when this card's spec equals the visitor's own character's spec, a small
    `pill` reading "Your spec" sits beside the role label, `pill-site` token (gold), never a
    second colour invented for this one case.

### 4.C `/guides/<class>/<spec>` header + 3-up rail — `ArtPanel` + `ClassHeader` (full) +
new `GuideActionRail.astro`

**Header**, identical component and props shape to `/bis/<class>/<spec>` (`ClassHeader`,
non-minimal) with two differences justified below:
- `bands`/`faction`/`race`/the controls row (`BandTabs`, `FactionToggle`, race select) are
  **omitted** — a guide is not banded or factioned content the way a BiS list is (there is one
  guide per spec, not one per band/faction combination), so `ClassHeader` renders here closer
  to its `minimal` mode but **keeps** the one summary sentence `minimal` normally drops: a
  guide's h1 alone ("Fury Warrior in Forever") carries less information than BiS's banded h1
  does, so the one-line summary earns its place here specifically. This is a **third render
  mode** for `ClassHeader`, named exactly: `minimal` plus a caller-supplied summary string
  (one new optional prop, `summaryOverride?: string`), not a fourth boolean flag maze — the
  build lane's own design review per tenet 10, same as `LogsHero` was for the logs rebuild.
  - Summary sentence, 14px `#c9c2b2`: the guide's own `description` frontmatter, unchanged
    (already written as exactly this kind of one-line summary).
- `SpecTabs` **is** kept, linking to this class's other two spec guides — unlike BiS's version,
  every tab here is always active-capable (no healer/tank "no data" branch: every one of the
  twenty-seven spec guides exists, confirmed by the file count in this spec's own header), so
  no `minimal`/empty branch is needed here at all.

**`GuideActionRail.astro`**, new, directly under the header, full-bleed band background
(`ArtPanel`'s own gradient continues under it, matching how BiS's `three-panel-row` sits
inside the same `ArtPanel` as its header) — three `panel-box` cards, `grid-cols-3` desktop /
stacked phone, the exact `gap-16px` row BiS's own `.three-panel-row` already uses:

1. **Build card.** Label `Build` (the `label` token). A 120px-tall non-interactive thumbnail of
   the build's own tree — `GuideBuildTree` rendered at a fixed `max-h` with
   `pointer-events:none` and no scroll, just enough to show shape and a few lit nodes, not a
   readable tree (the full tree still renders below, unchanged, under "Talents and builds" —
   this is a preview, never a duplicate of the real thing). Under it, `BuildActionButtons`
   (kept component, unchanged props) — "Load this build" / "Sim this build".
2. **Rotation card.** Label `Rotation · {bandTopLevel(60)}` i.e. `Rotation · 60` (mirroring
   BiS's own `Play it · {bandLabel}` convention, `PlayItPanel`'s own heading pattern) — the
   first **four** lines of this spec's own level-60 rotation entry
   (`rotationLinesFor(rotationEntryFor(entries, 60), ...)`, the exact function BiS's
   `PlayItPanel` already calls, reused unchanged), each rendered exactly as `PlayItPanel`
   already renders a line (icon 28px, name, rank if any, condition sentence in full — **never**
   CSS-truncated, tenet 4). Under the fourth line, a text link `Full priority ↓` scrolling the
   page to the "Rotation and priority" section's own `id` (`#rotation-and-priority`, the
   existing `slugify` output) — not a second rotation list, a jump to the one that already
   exists below.
3. **Stat priority card.** Label `Stat priority`. **Revised, round-1 mock review finding 4**
   (the bare `StatPriorityPills` row left roughly 180px of dead panel below six short pills,
   next to a Build card and a Rotation card that both actually use their height): this card now
   shows one line per stat, ordered exactly as `StatPriorityPills` already orders them, each
   line carrying its real per-point scale number — `StatWeightsPanel`'s own convention (scale
   factor normalized so the top *significant* stat at this band = 1.00), read from the same
   band's own `weights[]` the BiS page already reads, trimmed to the one number a glance needs
   (no bar, no error column, no "per point"/"addon" footer — those stay `StatWeightsPanel`'s own
   job on `/bis`, never duplicated here). An insignificant stat prints `Not significant`,
   `StatWeightsPanel`'s own existing copy, instead of a number. **Chosen over the other option
   the finding offered (`align-items:start`, letting the three cards size to their own content):
   `/bis`'s own `.three-panel-row` already stretches its three panels to equal height with no
   `align-items` override, and the three rail cards here are meant to read as the same family —
   filling the card honestly with real numbers keeps that match, instead of introducing the
   first unequal-height row in the class-page-header family.** The prose section below keeps its
   own plain, number-free `StatPriorityPills` copy exactly as `[spec].astro` already renders it
   (unchanged, §3's "kept" list) — the rail's version is the only one carrying weight numbers,
   so the two never show conflicting content for the same question.

### 4.D Prose sections — kept order, one new planted region (Leveling)

The nine sections render in their existing fixed order (`SPEC_SECTIONS`, unchanged), each
through the existing `renderGuideMarkdown` pass, with the existing three planted components
(`GuideBuildTree`+`BuildActionButtons` under "Talents and builds", `StatPriorityPills` before
"Stat priority" prose, `RacePillRow` before "Races" prose) in their current positions,
**unchanged** — §4.C's rail does not remove any of this, it answers the same questions faster
for a visitor who stops at the fold.

**Readability, new:** `.prose-forever p`, `.prose-forever ul`/`ol` gain `max-width: 68ch` (a
new rule, this spec's own addition to `global.css`) — the article column is 820px wide
(`Content.astro`'s own `lg:max-w-[820px]`), which at Barlow 16px/1.6 runs roughly 95-100
characters per line, past the 60-75ch comfortable-reading range every typography guide
(including this site's own `prose-forever` table styling, which already caps cell text
implicitly via its grid) assumes. Headings, the planted components (tree, pills, race row) and
the Leveling band strip below stay the full 820px column width — only running paragraph and
list text narrows. This is a **measured** fix, not a taste call: 820px ÷ ~8.5px average glyph
width at 16px Barlow ≈ 96 characters; 68ch at the same face is roughly 580px.

**Leveling section — new planted component, `LevelingBandStrip.astro` (proposed ruling, §10.1):**

Replaces the Leveling section's single paragraph of unanchored prose with the same real,
sim-checked per-band talent data the BiS page's own band tabs already show, formatted as a
five-row strip between the section heading and the existing leveling prose (same planting
convention as the other three sections: `proseOnly('Leveling')` keeps the prose, the strip
goes between the `## Leveling` heading and it).

- **Data:** this spec's own BiS file (`data/builds/<build>/bis/<spec>.json`), one row per
  `bands[]` entry **for one faction** — the guide's own first `recommendedRaces` entry decides
  which (fury's own `recommendedRaces: [human, troll]` → human → alliance; a guide whose first
  recommended race is a Horde one reads the horde rows instead — one deterministic rule, never
  a visible faction toggle on this page, since a guide is read once, not browsed by faction the
  way BiS's full gear list is).
- **Row, each:** `{bandLabel}` (`bisCopy.bandRangeLabel`, e.g. "20 to 29", or plain "60" at the
  top band, the existing BiS convention reused verbatim) · `{talent_points} points` ·
  `Load in planner` → `/planner?spec=<spec>&talents=<band.talents>` (the identical href shape
  `bis/[class]/[spec].astro` already builds for its own band panels — zero new URL contract).
  No DPS figure on this row (a leveling band's own `set_dps` is already shown, in context, on
  the BiS page for the player who wants it — repeating it here would be the exact "never
  restate a gear list" tenet 11 the planner/BiS split already established, and talent points
  spent is the one figure that is actually about *this* section's subject, talents, not gear).
- **Layout:** a single `panel-box` containing five rows, each row's own top line
  `grid-template-columns: 90px 1fr auto` (band label / points / button), 1px `border-line-soft`
  dividers between rows — the same shape as `bis`'s own "Where to get it" grouped list rows,
  reused rather than invented.
- **Thumbnail, desktop only (round-1 mock review finding 5, added):** under each row's top line,
  a non-interactive, wrapped row of that band's own *lit* talent icons (every talent across all
  three trees with `rank > 0` at that band, real decode of the same `talents` string the row's
  own point total already reads — 16px icons, a small rank badge only above rank 1), so a reader
  sees **which** points a band picks up, not only how many, without leaving the page. Growing
  real counts across the five Fury/Alliance rows: 3 (20 to 29), 8 (30 to 39), 10 (40 to 49), 14
  (50 to 59), 19 (60) — confirmed against the same decode the Build rail card and the full tree
  under "Talents and builds" already use, one decoder, never a second one. **Phone drops the
  thumbnail** (finding 5's own instruction): nineteen icons wrapped inside a 354px row at the
  bottom band would crowd the one piece of information the row cannot lose — `Load in planner`'s
  own 44px tap target — so the phone strip keeps all five rows' band label, point total and
  button, and nothing else; `Load in planner` stays one tap away either way, same as desktop.
- **Why this over the status quo:** the current Leveling section asserts "Fury is generally
  considered the strongest leveling spec" with zero concrete build guidance for any bracket —
  a visitor who wants to actually respec at 30 has to leave the page, open the planner cold,
  and guess. This strip is the one closing gap between "what this spec is" (the rest of the
  page) and "what do I click right now" (tenet 14's own standard, applied to the one section
  that previously had no actionable hand-off at all).

## 5. States, every region

## 8. Performance and polish limits

- **No layout shift on hydration.** `GuideBuildTree`'s existing `Skeleton` (already sized to
  the ready three-column grid) now additionally needs a **second**, smaller reserved height for
  its new thumbnail-scale rendering inside the rail card — the build lane measures the real
  thumbnail's rendered height and sizes the `Skeleton`'s `min-h` to match exactly, the same "no
  element's ready height differs from its loading placeholder" discipline every other deferred
  panel on the site already follows.
- **No missing-icon flash.** The rail's Rotation card icons and the class landing's spec-card
  icons are both resolved at **build time** (`specTabIcon`, `rotationLinesFor`'s own
  `iconFileExists` check) — no client fetch, no placeholder swap after paint; a line whose icon
  the build has no file for renders `PlayItPanel`'s existing placeholder square from first
  paint, never a broken `<img>`.
- **LCP candidate is the header h1** on all three surfaces (server-rendered, present before any
  island hydrates) — `GuideBuildTree`'s own client-rendered thumbnail sits **below** the h1 in
  paint order and is `client:visible`, unchanged from today's mechanism, so it cannot compete
  for the LCP slot.
- **Lighthouse budget (`web/lighthouserc.json`):** `/guides.html` and
  `/guides/warrior/fury.html` — performance ≥0.90, accessibility/SEO ≥0.95, **LCP ≤1700ms**
  (this surface's own budget row, tighter than BiS/Logs' 2200ms — confirmed in
  `lighthouserc.json`), TBT ≤100ms, CLS ≤0.05. The rail's three cards are all static markup
  (no new fetch beyond `GuideBuildTree`'s existing one, which was already on this page before
  this rebuild) — this spec adds no new network round trip that could move LCP against the
  tighter budget.

## 10. Rulings proposed for the owner

### 10.1 The Leveling section becomes a five-row band strip, not prose alone

**Proposal:** replace the Leveling section's single unanchored paragraph with a planted
`LevelingBandStrip` (§4.D) reading the spec's own BiS file — one row per band (20 to 29 through
60), each showing the real, sim-checked talent point total and a direct `Load in planner` link
built from that band's own verified talent string, the same data the BiS page's band tabs
already show.

**Reasoning:** the status quo Leveling section makes a claim ("Fury is the strongest leveling
spec") with no way for a reader to act on it — the next thing a leveling player needs is a
build for *this* bracket, and today that means leaving the guide, opening a cold planner, and
guessing. The data already exists, already verified (`bisCopy.verifiedTitle`'s own "Confirmed
by a Top Gear simulation pass" standard already applies to the exact strings this strip would
show), and is already surfaced on a sibling page — withholding it here is the "answer, not a
pointer to the answer" gap tenet 14 exists to close.

### 10.2 Race art stays the existing text-pill treatment, not a new asset

**Proposal:** ship `RacePillRow` exactly as it exists today (a coloured text pill, faction
colour only, no portrait) on every spec guide in this rebuild, and file "HD race portraits" as
a data/asset follow-up lane rather than inventing placeholder race art for this pass.

**Reasoning:** `RacePillRow`'s own header comment already states the ruling that produced it
("race portraits do not exist: use the race name in a pill with the faction colour, no
invented art") — this spec confirms rather than revisits that decision, since no race art has
shipped anywhere on the site since; inventing a square, a silhouette or an achievement-icon
stand-in here would violate tenet 7's "never redrawn, never restyled" rule the moment real
client race art lands and has to replace whatever was invented in its place.
