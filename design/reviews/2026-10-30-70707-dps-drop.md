# The 70707 raid DPS drop (2026-10-30)

The question: on the same talents and the same engine, every Mage raid band sims about 5% lower on 1.60.1.70707's item database than on 1.60.1.70658's. Is that a real Blizzard change or a data problem?

Nothing was committed, pushed or dispatched. All sims ran in a scratch worktree of `d7a009920` on the pinned engine `1f542def3`, with only `sim/internal/simdb/simdb.bin` swapped.

## Verdict: a data problem

**The client did not change these items. Wowhead's Forever gear-planner payload did.**

- The pipeline takes about 700 Forever items from wowhead's payload. These are items the client ships only as server hotfixes, so they have no `ItemSparse` row in wago's export.
- That payload is fetched live on every `data.yml` run. Nothing carries it forward between builds, and no gate compares a new build with the build before it.
- Wowhead's payload lost 292 of those items between the 70658 run (28 Oct) and the 70685 run (29 Oct).
- Of the 292:
  - **138 fell back to classic-db's 1.12 stats.** This includes the raid staves: Kindling Stave went from 60 spell power to 0, and Spire of Hakkar from 62 to 18.
  - **154 left the catalogue entirely.** Greaves of Withering Despair (22240), the item `carry-bis` stopped on, is one of them.

## 1. What changed between the builds

### The client's own rows (wago `ItemSparse`/`Item`): nothing that matters

`ItemSparse` for 70658 and 70707 was re-downloaded from wago.tools. The 70707 file is byte-identical to the lane's `raw/ItemSparse.csv`.

| | 70658 | 70707 |
|---|---|---|
| ItemSparse rows | 19,257 | 19,267 (+10, ids 288896–288931, none removed) |
| ItemSparse header | same 100+ columns | same, no schema change |
| Changed rows on shared ids | n/a | 43, none of them a stat column. The changes are Flags_0/1 (18), Display/ItemNameDescription (16), RequiredSkill (3), Description (3), Bonding, RequiredLevel and DmgVariance (1 each) |
| Item rows | 31,876 | 31,982 (+106, none removed) |
| `raw/hotfixes/` dump | 4,379 rows | byte-identical: it was seeded from the previous build, as `SEEDED_FROM` records |

Neither 11750 nor 10844 has ever had an `ItemSparse` row, in either build or in the hotfix dump. Both have `Item` rows in both builds.

### The wowhead supplement: 688, then 7, then 396

| build (bot run) | items.json | stats from wowhead | stats from classic-db | mage.json |
|---|---|---|---|---|
| 70630 | 25,678 | 688 | 1,359 | 4,008 |
| 70658 (28 Oct) | 25,678 | 688 | 1,359 | 4,008 |
| 70685 (29 Oct) | 25,365 | **7** | 1,727 | 3,908 |
| 70707 (30 Oct) | 25,534 | **396** | 1,497 | 3,978 |

- The supplement had grown steadily, from 428 items at 70009 to 688.
- The 7 items at 70685 are new ids (2889xx).
- 70707's 396 are a strict subset of 70658's 688. Nothing new came back, only part of what was lost: these are the "166 came back".
- Today's live payload (`nether.wowhead.com/forever/data/gear-planner?dv=100`, fetched 19:46 UTC) has 10,248 records, all `versionNum` 16001. It yields exactly 70707's 396 supplement items.
- Wowhead's own tooltip API now answers `{"error":"Entity not found"}` for Kindling Stave, Spire of Hakkar, 22240 and 10 of 12 randomly sampled lost ids. Sorcerer's Crown and Chains of the Lich still resolve.
- All 292 lost ids still have `Item` rows in the 70707 client. Blizzard has not deleted these items.
- The lost items are mostly level 40–60 and epic: 96 epic, 91 at level 60, 67 in the 50s. The kept ones are mostly level 20–30. A partial re-import on wowhead's side would look like this. A Blizzard itemization pass would not first fall to 7 and then come back.

## 3. Other specs

**It is not every raid band.** On today's BiS sets, the level-60 sims that drop are the ones whose BiS wears one of the two staves:

- Mage, all three raid bands;
- Warlock, all three raid bands;
- Affliction, Demonology and Destruction, bare at 60.

The level-60 BiS of Shadow, Balance and Elemental has no lost item. Neither do the physical specs' sets, beyond item 2100:

- **Item 2100, Precisely Calibrated Boomstick** (classic-db's 38–45 damage replaces wowhead's 29–55).
- **It sits in the rogue raid sets and the warrior-protection raid set.** Rogue Combat does not move. Survival hunter's bare band, which also wears it, does not move either.

The ranking itself is hit far more widely:

- 30 of the 292 items sit in some 70658 BiS band.
- Most are in the level-50 bands, and they cover nearly every spec. Examples:
  - Acumen Robes;
  - Rotgrip Mantle;
  - Spritecaster Cape;
  - Masons Fraternity Ring;
  - Gemburst Circlet;
  - Cape of the Black Baron for feral and hunters at 60.
- A forced re-rank on 70707 would quietly swap all of them out on vanilla stats, or for lack of the item.

## 4. The fix: pipeline only

Generated files stay as they are; the nightly owns them.

### a. Carry the wowhead supplement forward

This mirrors what `data.yml` already does for the hotfix dump.

- **`data/pipeline/wowhead_items.py`, `fetch_wowhead`:**
  - after validating the live payload, merge it into a committed record set, `raw/wowhead/items.json`: the parsed `ITEM_PAGE_DATA` records, keyed by id;
  - the set is seeded from the previous build;
  - live records win, and a seeded record the live payload no longer lists is kept;
  - an id is dropped only when the new client's `Item.csv` no longer has it, or the client now has an `ItemSparse` row for it, in which case the client is the truth;
  - log the carried count, and fail when live coverage of the seeded set falls below a floor (for example 90%) unless `--allow-shrink` is passed. 70685's 7 of 688 would have failed.
- **`load_items`/`raw_path`** read that merged file. This covers `normalize/wowhead.py`, `simdb`, `icons_fix`, `levels` and `classicdb_items`, so every consumer sees the same union.
- **`.gitignore`:** un-ignore `data/builds/*/raw/wowhead/items.json`, as is already done for `raw/hotfixes/*.csv`. The parsed subset is small; the 6.8 MB JS payload stays ignored.
- **`.github/workflows/data.yml`, "Seed the fill-in caches" step:** add `wowhead/items.json` to the `rel` list. This step has to move ahead of `fetch-wowhead`, which today runs before the seed.

### b. Make the catalogue floor cross-build

- **Where:** `data/pipeline/csvio.py` `check_item_sparse_completeness` and `data/pipeline/normalize/__init__.py` `_check_class_items_not_shrunk`.
- **The gap:** both compare only against the same build's own committed file, so a first-time build has `previous_count == 0` and always passes. That is why 70685's −313 items went through silently.
- **The change:** when the build has no committed `items.json`, fall back to the newest other build's count, using the same `sort -V` predecessor rule as the seed step.
- **A second gate:** add a gate on the wowhead-sourced count. A wowhead item that falls back to classic-db keeps the item count level while its stats are rolled back to 1.12, so the count gate alone cannot see it.

### c. Regenerate after a and b land

- Re-dispatch `data.yml` for 1.60.1.70707, and for 70685 if it is kept.
- Then re-run the BiS ranking.
- The Mage lane's "same, on 70707 items" column and its raid deltas should then match the 70658 column within error.
- The `carry-bis` stop on 22240 should go away on its own, because the item comes back.

### Open check, not blocking

- The client-truth confirmation that Kindling Stave really is 60 SP in-game today needs a fresh `DBCache.bin`. The one on this Mac is from 11 Oct.
- After the owner next logs in, `python -m pipeline hotfixes` would settle it. It would also add these rows to the hotfix dump, which outranks wowhead.
