# Retail v22 layout: what is measured and what is not

Measured over 89 real v22 logs (26,030,980 lines, builds 12.0.5, 12.0.7 and 12.1.0).
The plan at `docs/superpowers/plans/2026-09-16-retail-v22-layout.md` carries the full
field table; this file records only what could not be pinned, so that a later reader
knows which names in the code are evidence and which are placeholders.

## Advanced block offset 8: `Unknown8`

Zero for almost every unit in every log. Non-zero as a small per-unit constant for a
handful of players: 301, 402, 453, 597, 633, 1088. It matches no COMBATANT_INFO stat
field, does not move when the unit takes or absorbs damage, and does not track any
aura. It is counted so that the 19-field block's widths verify, and it is read into
`Advanced.Unknown8` so nothing silently shifts if it is later identified.

To identify it: find a character whose value is non-zero, and diff their
COMBATANT_INFO and equipped items against a character whose value is zero.

## Advanced block offset 7: `Versatility`, with a scale caveat

Offset 7 tracks versatility buffs and nothing else, and sits at a constant
1.8513x the COMBATANT_INFO versatility rating across 12 players in two independent
logs (spread 0.18; the runner-up field's spread is 0.79). Both logs are arena logs and
arena scales secondary stats, so the most likely reading is that COMBATANT_INFO reports
the PvP-adjusted rating and the advanced block reports the raw one: 1/1.8513 = 0.5402.

To confirm: run the same ratio over a raid or dungeon log, where the factor should be
1.0. Until then the name stands on the correlation, not on the scale.

## COMBATANT_INFO's fourth defensive rating

v22 writes four fields where v16 writes dodge, parry and block. All four are 0 in every
sample in the corpus, so which of the four is new cannot be told apart. The decoder
reads dodge, parry and block from the first three and ignores the fourth. Harmless
while they are all zero; revisit if a tank log ever shows non-zero values.

## `Advanced.Level` is item level, in v16 as well as v22

The v16 sample shows 189-191 in this field on a level-60 character, and v22 shows
281-339 on level-80 characters: both are item level, not character level. The v22
documentation names it correctly. Renaming the Go field would touch v16 decoding and is
out of scope for the v22 lane.

## `_SUPPORT` events are parsed and not counted

Version 22 emits SPELL_DAMAGE_SUPPORT, SPELL_PERIODIC_DAMAGE_SUPPORT,
RANGE_DAMAGE_SUPPORT, SWING_DAMAGE_LANDED_SUPPORT, SPELL_HEAL_SUPPORT,
SPELL_PERIODIC_HEAL_SUPPORT and SPELL_ABSORBED_SUPPORT: 88,075 lines across the 89-file
corpus. Each restates a slice of damage or healing already reported on an ordinary line,
attributing it to the player whose buff caused it.

The layout decodes them and records the supporting player in `Event.Supporter`. The
summary accumulator skips any event with a non-empty `Supporter`, because adding them to
the existing damage would double-count every augmented hit. Showing a supporter's
contribution is a report-design decision and is deliberately not made here.

## COMBATANT_INFO's talent field nests one level deeper in v22

v16 writes the chosen talents as a flat spell-id tuple, e.g. `(202751,262111,...)`. v22's
new talent trees write a list of `(nodeID, entryID, rank)` triples instead, e.g.
`[(90326,112183,1),(90328,112185,1),...]`. This is not a width change — the field is
still one comma-separated group at the same index — so it was not visible in the width
measurement in the plan doc. The talent index itself is correctly located: `intList`
would recurse into the part that does not parse as a bare integer and flatten every leaf
integer (nodeID, entryID and rank, interleaved) into one list, proving the position, but
that list is a wrong-but-typed value — `Combatant.Talents` is typed as, and consumed
elsewhere as, a flat spell-id tuple, and a flattened triple mix is neither.

One consumer reads the field: the web's planner link (`treeRanksFromTalents` in
`web/src/lib/report/planner-link.ts`) turns a combatant's `talents` into tree ranks, behind
a guard that rejects a list whose length does not match the tree. That guard is
coincidental, not structural — a v22 list happening to match a tree's expected length
would pass it and produce nonsense ranks — so it cannot be relied on to keep a v22 list
out.

Ruling (final review): for a v22 layout, `Combatant.Talents` is emitted empty rather than
the flattened triple mix, via `layout.Combatant.TalentsAreSpellIDs` (`false` for
`RetailV22`, `true` for `RetailV16`); `logs/engine/event/special.go`'s `readCombatant`
only calls `intList` on the talent field when the row says the result is spell IDs. This
is a currently-empty list carrying no data rather than one carrying wrong data, at the
cost of the planner link having nothing to offer a v22 combatant until this is revisited.
When the summary carries v22 talents as named triples, `readCombatant` gains a second,
named path for them and the web's planner link is the consumer to update.

## Acceptance: the 89-file corpus sweep

Re-runnable with `logs/scripts/v22-conformance.sh <log-dir>`. The corpus is 89 files and
7.3 GB and is not in the repository.

| | before (engine at main) | after |
|---|---|---|
| files | 89 | 89 |
| lines | 26,030,980 | 26,030,980 |
| layout | `inferred`, unverified, on every file | `retail-v22`, verified, on every file |
| parse errors | 6,725,218 (26%) | 0 |
| fights | 2,958 | 2,395 |
| distinct unknown events | 41 | 0 |

Every one of the 89 rows in `conformance-v22-after.jsonl` shows
`layout=retail-v22 layout_verified=true layout_inferred=false parse_errors=0
unknown_events={}` on the first run of the sweep script; no width outlier and no
unnamed event turned up, so no layout or test change was needed for this task. The
fight count changed from the baseline (2,958) because the baseline's inferred layout
was desynchronizing mid-line on 26% of lines, which fabricates and destroys fight
boundaries; 2,395 is the count under a layout that reads every line correctly.

A bare `DAMAGE_SHIELD` (as opposed to `DAMAGE_SHIELD_MISSED`, which is registered) is
unregistered in `RetailV22`: the `DAMAGE_SHIELD` prefix exists only so that
`DAMAGE_SHIELD_MISSED` splits correctly, and there is no `_DAMAGE` (or other) suffix
paired with it, matching the fact that WoW's `_MISSED` suffix is the only one the game
ever writes for a reflected-damage-shield line. It does not occur in the 89-file corpus
(0 occurrences), so this is untested against a real line; if one ever appears it lands as
`Unknown` (kept raw), the row's honest response to a shape it does not name, rather than
a parse error.

## Probe files: fight counts, not the number this plan predicted

The plan's acceptance text asked to confirm `retail-1207-small.txt` and
`retail-1210-pvp.txt` parse to 5 and 19 fights. Running the built binary (the same one
the corpus sweep uses) gives 4 and 6:

```
$ /tmp/forever-logs fights -json .../logs/v22/retail-1207-small.txt | wc -l
4
$ /tmp/forever-logs fights -json .../logs/v22/retail-1210-pvp.txt | wc -l
6
```

Both parse with `parse_errors=0` and `unknown=0` under `retail-v22 verified=true`. The
predicted 5/19 does not match either file under the engine this branch produces.
Fight segmentation for both files is driven entirely by combat-gap detection
(`ARENA_MATCH_START`/`END` are specials, not fight boundaries, by this plan's own
design — see Task 2/3), which this task's brief does not authorize changing, so this
is recorded here as a discrepancy against the plan's predicted numbers rather than
"fixed" by widening the segmenter.

The player-count claim does hold, but only for the fight that is the actual rated
arena: `retail-1207-small.txt` has 12 `COMBATANT_INFO` rows for 6 distinct players
(the file's Solo Shuffle match restarts mid-log, re-emitting `COMBATANT_INFO` for the
same six), and fights 1-2 (the arena window between the file's `ARENA_MATCH_START` and
`ARENA_MATCH_END`) list exactly those 6 players. `retail-1210-pvp.txt` has 6
`COMBATANT_INFO` rows for 6 distinct players, and fight 1 (`Black Rook Hold Arena`)
lists exactly those 6. Both files continue past the arena into unrelated content — a
Silvermoon City scene in the first file, a Battle for Gilneas battleground in the
second — with 15-20 other players who have no `COMBATANT_INFO` row in the file at all,
which is why the whole-file fight and player counts do not reduce to a single "6 and
6": only the arena portion of each file was ever meant to carry that signal, and it
does.
