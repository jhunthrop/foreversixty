## Engine version

One string identifies the engine build everywhere: `ENGINE_VERSION`, the short commit sha of
`wowsims-forever` the artifacts were built from, e.g. `7779ebb`. It appears in:

- `sim/enginever/version.go`: `const Version = "7779ebb"` (generated by `make engine-pin`).
- `web/public/_sim/<ENGINE_VERSION>/sim.wasm` and `sim.js` (immutable cache).
- Every `SimEnvelope.engine_version`, every stored sim row, every validation row.
- The premium lane's container image tag.

A result produced by a different `ENGINE_VERSION` than the current one is still readable and is
labelled stale in the UI; it is never silently re-run.

## Identifiers

- `sim_id`: 12 lowercase base32 characters from 60 random bits, same generator and alphabet as
  `report_id` (`api/internal/ids`). Route `/sim/<sim_id>`.
- `character_key`: unchanged from the logs contract, `<region>/<ruleset>/<name-slug>`.
- `spec_slug`: `<class-slug>-<spec-slug>` in lower kebab, e.g. `warrior-fury`, `mage-frost`. The
  canonical list lives in `data/curated/specs.json` (data lane) and is generated into
  `sim/specs/specs.go` and `web/src/lib/sim/specs.ts`. Nothing hardcodes a spec list elsewhere.

## The sim request and result envelopes (`sim/api`)

Go definitions in `sim/api/envelope.go`, mirrored in TypeScript at `web/src/lib/sim/types.ts`.
JSON field names are authoritative and identical in both.

```go
type SimRequest struct {
    EngineVersion string          `json:"engine_version"`
    Spec          string          `json:"spec"`            // spec_slug
    Source        CharacterSource `json:"source"`
    Encounter     EncounterSpec   `json:"encounter"`
    Iterations    int             `json:"iterations"`      // 500, 3000 or 10000
    RandomSeed    int64           `json:"random_seed"`     // 0 means random; paired runs set it
    Raw           []byte          `json:"raw"`             // proto-encoded wowsims RaidSimRequest
}

type CharacterSource struct {
    Kind        string `json:"kind"`         // "armory" | "addon" | "build" | "fight" | "manual"
    Ref         string `json:"ref"`          // character_key | "" | build id | "<report_id>:<fight_index>"
    CapturedAt  string `json:"captured_at"`  // RFC3339
}

type EncounterSpec struct {
    DurationSec  int     `json:"duration_sec"`   // default 180
    Variation    float64 `json:"variation"`      // default 0.2
    Targets      int     `json:"targets"`        // default 1
    ExecuteRatio float64 `json:"execute_ratio"`  // default 0.25
    Profile      string  `json:"profile"`        // "" | "patchwerk" | "encounter:<encounter_id>"
}
```

`Raw` is the engine's own `RaidSimRequest` protobuf (raid, encounter, sim_options), built by the
web from the character model, or by the API for validation runs. Both lanes pass it to the engine
untouched: the engine never sees our envelope.

```go
type SimResult struct {
    SimID         string          `json:"sim_id,omitempty"`
    EngineVersion string          `json:"engine_version"`
    Request       SimRequest      `json:"request"`           // Raw omitted when stored
    Lane          string          `json:"lane"`              // "browser" | "server"
    DPS           Estimate        `json:"dps"`
    IterationsRun int             `json:"iterations_run"`
    DurationMS    int64           `json:"duration_ms"`       // wall clock of the run
    Summary       summary.Summary `json:"summary"`           // logs engine shape, section below
    Error         string          `json:"error,omitempty"`
}

type Estimate struct {
    Mean   float64 `json:"mean"`
    StdDev float64 `json:"stddev"`
    Error  float64 `json:"error"`   // standard error of the mean
    Min    float64 `json:"min"`
    Max    float64 `json:"max"`
}
```

## The adapter: engine result to logs summary (`sim/adapter`)

`func Summarize(res *proto.RaidSimResult, req SimRequest) (summary.Summary, error)` in
`sim/adapter`. It builds `logs/engine/summary.Summary` (unchanged, do not edit `logs/`) so the
report components render a sim with no second renderer. Mapping, field by field:

| Summary field | From |
|---|---|
| `EngineVersion` | `"sim:" + ENGINE_VERSION` |
| `FightIndex` | `1` |
| `DurationMS` | `avg_iteration_duration * 1000` |
| `DamageDone` | one `Actor` for the player from `PlayerMetrics.actions` (`ActionMetrics` → per-ability rows: casts, hits, crits, misses, dodges, parries, glances, damage), plus one per pet |
| `DamageTaken`, `Healing`, `HealingTaken` | empty at launch; healing populated when a healing spec ships |
| `Auras` | `PlayerMetrics.auras` (`AuraMetrics`: uptime, procs) → `AuraTrack` |
| `Casts` | `ActionMetrics` cast counts → `CastRow` |
| `Resources` | `PlayerMetrics.resources` (`ResourceMetrics`) → `ResourceTrack` |
| `Roster` | one `RosterRow` for the player: name, class, spec, ilvl, talents |
| `Deaths`, `Interrupts`, `Dispels`, `Threat`, `Combatants` | empty |

Numbers that the engine reports per iteration are divided to per-fight averages before they enter
the summary; the raw distribution stays in `SimResult.DPS`. The adapter has a golden test per spec:
a checked-in engine result fixture and its expected summary JSON.

## API (`api/internal/sims`)

All routes under the existing envelope `{ ok, data, error, request_id }` and the existing session
and CSRF rules.

| Route | Auth | Request | Response |
|---|---|---|---|
| `POST /v1/sims` | optional session | `SimResult` with `Lane: "browser"` and `Raw` omitted | 201 `{ sim_id }`; saves a browser-run result |
| `GET /v1/sims/{sim_id}` | none | | 200 `SimResult` |
| `GET /v1/sims?mine=1&page=` | session | | 200 `{ rows: [ { sim_id, spec, dps, engine_version, created_at, title } ], total, page, per_page: 100 }` |
| `POST /v1/sims/run` | session + CSRF + premium | `SimRequest` with `Raw` set | 202 `{ sim_id }`; dispatches the Cloud Run job |
| `GET /v1/sims/{sim_id}/progress` | none | | 200 `{ state: "queued"\|"running"\|"done"\|"error", iterations_done, dps? }` |
| `GET /v1/specs` | none | | 200 `{ specs: [ { spec, state: "validated"\|"in_progress"\|"unsupported", median_gap, parses, worst_actions: [ { name, sim_casts, actual_casts } ], engine_version, updated_at } ] }` |
| `GET /v1/characters/{character_key}/sim-input` | optional session | | 200 `{ spec, gear, talents, buffs, captured_at, source }`: the character model from the newest of Armory, addon export, or last fight |

`GET /v1/rankings` gains `execution` to the sortable metrics and every row gains
`execution_score float|null`. `GET /v1/characters/{…}` and `GET /v1/guilds/{…}` rows gain the same
field. Null means the spec is not validated or the fight predates scoring.

**Premium flag**: `users.premium boolean not null default false`, set by hand until payments exist.
`POST /v1/sims/run` answers 402 with code `premium_required` when it is false.

**Parse job**: `api sim-run <sim_id>` is a Cloud Run job on the same image as the API, created once
by hand like `parse-report`.

**Execution score at fight close**: the ingest's fight-close path enqueues a scoring task when the
fight's player is a signed-in member and the spec is validated. The task runs the native engine
with the fight's recorded gear, talents, and buffs, and writes
`fight_metrics.execution_score = actual_dps / simmed_dps`, clamped to [0, 2].

## Postgres (migration 0006, api lane)

```sql
alter table users add column if not exists premium boolean not null default false;
alter table fight_metrics add column if not exists execution_score numeric;
create index if not exists fight_metrics_execution_idx
  on fight_metrics (encounter_id, difficulty, spec, phase, execution_score desc);

create table if not exists sims (
  id             text primary key,
  user_id        bigint references users(id) on delete set null,
  spec           text not null,
  engine_version text not null,
  lane           text not null,
  dps_mean       numeric not null,
  dps_error      numeric not null,
  iterations     int not null,
  title          text,
  result         jsonb not null,       -- SimResult with Raw omitted
  state          text not null default 'done',
  created_at     timestamptz not null default now()
);
create index if not exists sims_user_idx on sims (user_id, created_at desc);

create table if not exists sim_specs (
  spec           text primary key,
  state          text not null,        -- validated | in_progress | unsupported
  median_gap     numeric,
  parses         int not null default 0,
  worst_actions  jsonb not null default '[]',
  engine_version text,
  updated_at     timestamptz not null default now()
);
```

## Data pipeline (data lane)

Three new outputs from `python -m pipeline`, all under the existing build directory:

- `simdb` command → `data/builds/<build>/simdb.bin`: the engine's `SimDatabase` protobuf (items,
  enchants, item sets, consumables) generated from the same normalized tables the planner uses.
  Committed, since the engine needs it at build time.
- `simconst` command → `data/builds/<build>/spellconst/<class-slug>.json`: per-spell constants
  keyed by spell id (base points, coefficients where readable, cooldown ms, cast time ms, cost,
  duration ms, school, family mask), for the engine's generated constants files.
- `data/curated/apl/<spec_slug>.json`: the default rotation per spec, an `APLRotation` protobuf in
  its JSON form plus `{ "sources": [ { label, url, kind } ], "notes": "" }`. Validated by the data
  tests against the engine's APL schema.
- `data/curated/specs.json`: the canonical spec list, `[ { spec, class_slug, spec_slug, name,
  role, tree_index } ]`.

## Engine (engine lane, in the engine repo)

Binding for the other lanes:

- The protobuf API does not change shape. Lanes consume `RaidSimRequest`, `RaidSimResult`,
  `SimDatabase`, `APLRotation` as they are.
- `Stat` enum: `MeleeHit`+`SpellHit` → `Hit`, `MeleeCrit`+`SpellCrit` → `Crit`. Indexes stay
  synced between `sim/core/stats` and `proto/common.proto`. The web reads stat names from the
  proto enum, so this is the only place the rename surfaces outside Go.
- Two artifacts per version: `sim.wasm` + `sim.js` (the `syscall/js` glue) for the browser, and a
  `forever-sim` binary for the server lane. Both built in CI from the pinned sha.
- The WASM entrypoints the web uses: `raidSimAsync`, `raidSimRequestSplit`,
  `raidSimResultCombination`, `computeStats`, `abortById`. No others.

## Web (web lane)

- Routes: `/sim` (the sim page), `/sim/<sim_id>` (a saved result), `/sim/specs` (support page).
  `/sim` and `/sim/specs` are static shells; `/sim/<sim_id>` is a static shell whose OG tags the
  Worker rewrites from the API, exactly as `/reports/<id>` does today.
- One island, `sim-island`, built as a separate entry like `planner-island.js`, loaded on all
  three routes. The engine's wasm loads after first paint, from
  `/_sim/<ENGINE_VERSION>/sim.wasm`, in a worker pool sized `min(8, hardwareConcurrency)`.
- The character model is `web/src/lib/sim/character.ts` and is shared with the planner: the
  planner's `BuildDraft` (class_id, race_id, tree_version, point_order, gear) plus buffs,
  consumables, and the source. Loading a planner build into the sim and opening a sim's character
  in the planner are the same conversion in both directions.
- Compare mode reads the fight summary from the report's existing `data_base_url`; no new API.
- `web/src/lib/sim/worker.ts` owns the pool; `web/src/lib/sim/run.ts` owns request building and
  partial-result combination. Neither imports Astro.
