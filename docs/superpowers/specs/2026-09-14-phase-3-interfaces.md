# Phase 3 interface contract (logs product)

Binding for the three Phase 3 plans (api, companion, web). The spec is
`docs/superpowers/specs/2026-09-13-logs-engine-design.md` (sections 1 to 10); the engine it builds
on is merged at `logs/` (module `github.com/jhunthrop/foreversixty/logs`). Values here are verbatim.
Where the engine's exported types already define a shape (summary.Summary, store.Report,
store.Keys, session.Health), that Go type is the contract and this file names it rather than
copying it.

## Identifiers

- `report_id`: 12 lowercase base32 characters from 60 random bits, generated by the API at
  report creation. Never derived from content.
- `fight_index`: 1-based (the engine numbers fights from 1) integer, the engine's `fight.Fight.Index`.
- `device_id`: 16 lowercase base32 characters; `device token`: `fsd_` + 32 random base32
  characters, shown once, stored as SHA-256.
- `user_id`: bigint. `character_key`: `<region>/<ruleset>/<name-slug>`. `ruleset` is one of `normal`, `pvp`, `rp`, `hardcore` (Forever has no realms; the Deep Dive panel replaced them with four rulesets per region). `name-slug` is the two-part character name lowercased with spaces as `-`. The combat log identifies units as `Name-Realm` today; on Sept 17 the beta log settles what the realm segment carries for Forever and the parser maps it to `ruleset`.
- Regions: `us`, `eu`, `kr`, `tw`, `cn`. Realm slugs are lowercase with hyphens.

## Authentication

- **Browser sessions.** Cookie `fs_session` on domain `.foreversixty.gg`, `HttpOnly; Secure;
  SameSite=Lax; Path=/`, value an opaque 32-byte base64url id, 30-day expiry, stored in
  `sessions`. CSRF: cookie `fs_csrf` (readable) and header `X-CSRF-Token` must match on every
  state-changing request with a session; device-token requests are exempt.
- **Battle.net.** `GET /v1/auth/battlenet/start?next=/logs` sets a state cookie and redirects to
  `https://oauth.battle.net/authorize` with scope `openid wow.profile`; `GET
  /v1/auth/battlenet/callback` exchanges the code, reads `/oauth/userinfo` for `sub`
  (battletag id) and `battletag`, upserts the user, creates a session, redirects to `next` on
  `https://foreversixty.gg`. Client id from `BNET_CLIENT_ID`, secret from `BNET_CLIENT_SECRET`,
  redirect `BNET_REDIRECT_URL` (already registered for prod and localhost:8080).
- **Email magic link.** `POST /v1/auth/email {email}` sends a link with a 20-minute single-use
  token through the existing Resend mailer; `GET /v1/auth/email/callback?token=` creates the
  session. Rate limit 5 per email per hour.
- **Devices.** `POST /v1/devices/pair` (session) returns `{ code }` valid 10 minutes, shown on
  the site; the companion posts `POST /v1/devices/claim { code, name, platform }` and receives
  `{ device_id, token }` once. Companion requests send `Authorization: Bearer fsd_…`.
  `GET /v1/devices` lists, `DELETE /v1/devices/{id}` revokes.
- `GET /v1/me` → `{ user: { id, battletag, email, role }, characters: [...], guilds: [...] }` or 401.

## Ingest (companion → API)

All bodies are JSON unless noted; all responses use the envelope.

| Route | Auth | Body | Response |
|---|---|---|---|
| `POST /v1/reports` | device or session | `{ title?, visibility, zone?, logging_character? { region, ruleset, name } }` | 201 `{ id, created_at }` |
| `PUT /v1/reports/{id}/fights/{n}` | device | multipart: `summary` (JSON, `summary.Summary`), `events` (Parquet bytes), `metrics` (JSON `[]MetricsRow`), `raw_range` (JSON `{ start_offset, end_offset, sha256 }`) | 201 `{ fight_index, verified: true }`; 200 if already stored with the same sha; 409 `{ error: { message, fields: { metrics: "…" } } }` on verification mismatch |
| `PUT /v1/reports/{id}/fights/{n}/live` | device | `{ summary: summary.Summary, elapsed_ms, updated_at }` | 204; the API writes `live.json` and touches `report.json` |
| `PUT /v1/reports/{id}/raw?offset=N` | device | body `application/zstd`, ≤ 8 MiB; header `X-Raw-SHA256` | 204; 200 if the offset is already stored; 409 if the offset overlaps a different stored range |
| `POST /v1/reports/{id}/complete` | device | `{ final_offset, engine_version, health: session.Health }` | 204; schedules the raw-sample verification |
| `POST /v1/uploads` | session | `{ size_bytes, filename }` | 201 `{ upload_id, parts: [ { number, url } ], complete_url }` signed R2 multipart URLs, 1-hour expiry, part size 64 MiB |
| `POST /v1/uploads/{upload_id}/complete` | session | `{ etags: [ { number, etag } ], title?, visibility }` | 202 `{ report_id }`; enqueues the parse job |
| `GET /v1/reports/{id}` | any (visibility applies) | | 200 `{ id, title, visibility, owner: { id, battletag }, guild?, zone, status: live \| complete \| processing \| failed, engine_version, fights: []FightEntry, players: [], created_at, data_base_url }` |
| `PATCH /v1/reports/{id}` | owner or guild officer | `{ title?, visibility?, guild_id? }` | 200 |

`MetricsRow` (one per player per boss fight; `logs/engine/summary` exposes it as `summary.MetricsRow`
already if present, else the API defines it and the companion copies): `{ player_guid, name,
class, spec, role, ilvl, metric_dps, metric_hps, damage_taken, active_ms, deaths, encounter_id,
difficulty, size, duration_ms, kill }`.

**Verification.** On each fight PUT the API reads the Parquet events with the engine's reader,
rebuilds `summary.Summary` with `summary.New` fed the events, derives `[]MetricsRow`, and compares
to the posted `metrics` field by field (integers exact, floats within 0.5%). On mismatch the
fight is stored with `verified=false`, excluded from rankings, and the report flagged. After
`complete`, a job re-parses two random fights from the stored raw chunks and compares events;
mismatch flags the report `tampered` and removes its rankings rows.

**Whole-file parse job.** `api parse-report <report_id>`: streams `uploads/<upload_id>/raw.txt.zst`
from R2 through `session.Feed`, writes fights through `store.Publisher` with an R2 `Putter`,
inserts fights and metrics as they close (so the page fills progressively), sets status
`complete` or `failed` with the health record.

## Storage

- R2 bucket `foreversixty-logs`, keys exactly as `store.Keys`: `reports/<id>/report.json`,
  `reports/<id>/fights/<n>/summary.json`, `reports/<id>/fights/<n>/events.parquet`,
  `reports/<id>/fights/<n>/live.json`, `reports/<id>/raw/<offset>.zst`, plus
  `uploads/<upload_id>/raw.txt.zst` for whole-file uploads. Cache-Control: `public, max-age=31536000,
  immutable` on summary.json and events.parquet; `public, max-age=5` on report.json and
  live.json; `private` on raw.
- API credentials: `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET`
  (S3-compatible endpoint `https://<account>.r2.cloudflarestorage.com`); the API's Putter is an
  S3 client; tests use `store.Dir`.
- **Delivery.** The site Worker binds the bucket as `LOGS` and serves
  `GET /logs-data/reports/<id>/...` from it for reports whose visibility is public or unlisted,
  with the Cache-Control above passed through. For private and guild reports the island calls
  `GET /v1/reports/{id}/access` (session) and receives `{ data_base_url }` pointing at signed R2
  URLs valid 10 minutes; the Worker refuses `/logs-data/` for those reports. `GET /v1/reports/{id}`
  returns `data_base_url` = `https://foreversixty.gg/logs-data/reports/<id>` for public/unlisted.
  The Worker learns visibility by fetching `GET /v1/reports/{id}/visibility` (cached 60 s).

## Report page (web)

- `/reports/<id>` is served by the Worker as the static shell `reports.html` for any id, with OG
  tags injected from `GET /v1/reports/{id}` (title, zone, fight count, `og:image` =
  `https://api.foreversixty.gg/reports/<id>/card.png` rendered by the API like build cards).
  The island (`ReportView.svelte`, `client:load`) reads the id from the URL, fetches
  `GET /v1/reports/{id}`, then `report.json`, and each fight's `summary.json` on demand;
  `events.parquet` loads only when a deep interaction (brush, filter, drill-down) first happens,
  through DuckDB-WASM loaded lazily from the site's own assets.
- URL state: `?fight=<n>&mode=analyze&view=tables&tab=damage-done&source=<guid|friendlies|enemies>&start=<ms>&end=<ms>`.
- Tabs and views exactly as spec section 4. The island is a separate entry like
  `planner-island.js` and shares `global.css`.
- `/logs`: sign-in gate, "Live logging" instructions with the companion download and pairing
  code, whole-file upload with progress, "Your reports" list.
- `/rankings/<encounter-slug>`, `/character/<region>/<ruleset>/<name>`, `/guild/<region>/<ruleset>/<name>`:
  Worker-served shells with islands reading the API; OG tags from the API's JSON.
- `/login`, `/account` (devices, characters, anonymize toggle, sign out).

## Companion (Go)

- Module `companion/`; binaries `foreversixty-companion` for darwin/arm64, darwin/amd64,
  windows/amd64, linux/amd64. Config and state under the OS app-data directory
  (`~/Library/Application Support/ForeverSixty`, `%APPDATA%\ForeverSixty`, `~/.config/foreversixty`):
  `config.json { api_base_url, device_token, wow_paths: [], report_visibility }`, `queue/`
  for pending bundles and chunks, `state/<report_id>.json` from `session.State()`.
- Detects WoW installs from known paths and a picked folder; watches `Logs/WoWCombatLog*.txt`
  (the game may rotate with a timestamp suffix); a new file or a size increase after an idle gap
  longer than 30 minutes starts a new report.
- Runs `session.Feed` on appended bytes; on each closed fight builds the multipart bundle and
  PUTs it; every 5 seconds while a fight is open PUTs `live`; streams raw chunks of 4 MiB zstd
  in the background with `offset`; on file end plus 15 minutes idle POSTs `complete`.
- Queue on failure, retry with backoff, resume by offset; at-least-once is safe by contract.
- Addon sync: after logout (SavedVariables file mtime change) reads
  `WTF/Account/<acct>/SavedVariables/ForeverSixty.lua` and POSTs its exports to
  `POST /v1/addon/exports` (device) `{ characters: [ { name, ruleset, region, export: "FS1:…" } ] }`;
  writes `ForeverSixtyInbox.lua` with builds from `GET /v1/addon/inbox` (device) at startup and
  every 10 minutes. Both endpoints are owned by the api plan; the addon side is Phase 2.
- UI: system tray with a native webview window over `companion/ui/index.html` using the site's
  tokens; pages: status (logging state, current report link), reports, devices/sign-in, settings.
  Signing and notarization are release-workflow tasks gated on user-owned credentials
  (`APPLE_*`, `WINDOWS_SIGNING_*` secrets); unsigned builds are produced regardless.
- Auto-update: checks GitHub Releases `latest` on start and every 6 hours; downloads the asset,
  verifies a minisign signature with a public key embedded at build time, swaps on next launch.

## Amendments (Sept 14, after the three plans were cross-checked)

These override the sections above where they differ. Rulings are recorded in the scratchpad
cross-check table; the api plan is the server and the web and companion plans follow it.

- `fight_index` is 1-based everywhere (the engine's own numbers).
- `X-Raw-SHA256` on `PUT /v1/reports/{id}/raw` is the SHA-256 of the **decoded** (uncompressed)
  chunk bytes; the server derives the end offset from the decoded length and bounds decoding at
  16 MiB. Chunks are 4 MiB of uncompressed log, zstd-compressed, boundaries on multiples of 4 MiB
  from the report start; all offsets are report-relative.
- `GET /v1/reports?mine=1&page=` (session): `{ rows: [ { id, title, zone, status, visibility,
  created_at, fight_count, kill_count } ], total, page, per_page: 100 }`.
- `DELETE /v1/sessions` (session + CSRF) signs out, clears both cookies, 204.
- `PATCH /v1/me { anonymize: true }` (session + CSRF) returns the updated `me` object.
- `GET /v1/devices` returns the device array directly as `data`.
- `POST /v1/devices/pair` returns `{ code, expires_in }` (seconds).
- `GET /v1/rankings` and `GET /v1/rankings/guilds` accept `encounter=` as either the numeric
  encounter id or the encounter slug used by `/rankings/<encounter-slug>`. Guild rows have no
  `state` field.
- `GET /v1/characters/{region}/{ruleset}/{name}`: `best[]` and `history[]` rows are
  `{ encounter, encounter_id, difficulty, metric, value, percentile?, spec?, fought_at,
  report_id, fight_index }` where `encounter` is the display name; `builds_seen[]` is
  `{ talent_split, spec?, first_seen }` (without `build_id`: a planner build hashes spend order,
  which the log does not record).
- `GET /v1/guilds/{region}/{ruleset}/{name}`: `progression[]` rows are `{ encounter,
  encounter_id, difficulty, kills, pull_count, first_kill_at? }`; `roster_best[]` rows are
  `{ player: { key, name, class, spec }, encounter, encounter_id, metric, value, fought_at }`.
- Whole-file uploads accept up to 4 GiB on both sides.
- `GET /v1/addon/inbox` (device) returns `{ builds: [ { id, name, character?, code } ] }` where
  `code` is the build's FSB1 addon code; `POST /v1/addon/inbox` (session) exists on the API and its
  web caller (the planner's "send to my addon" control) ships with Phase 2, not Phase 3.
- `POST /v1/addon/exports` normalises an unrecognised `ruleset` value through the API's single
  realm-to-ruleset mapping function instead of rejecting it; the companion forwards whatever the
  addon wrote.
