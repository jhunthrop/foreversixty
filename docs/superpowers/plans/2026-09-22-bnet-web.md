# Bnet-web (Battle.net character import: web) Implementation Plan

**Goal:** Build the web half of the Battle.net character import spec: `Me`/`MeCharacter`
grow the section 6 fields, the account page's Characters section moves into
`CharacterList.svelte` with realm/level/guild-line rendering and an empty/imported state,
`?refreshed=1` shows a toast, `AddonPasteBox.svelte` saves a signed-in paste to the account
via a new `postMyExports`, and `CurrentCharacterBar.svelte` shows the guild line for an
armory-sourced current character — all stubbed against the not-yet-landed `bnet-api` lane's
`/v1/me` and `/v1/me/exports` shapes exactly as the existing account/billing specs stub theirs.

**Spec:** `docs/superpowers/specs/2026-09-22-battlenet-character-import-design.md` (binding).
Scope is section 7, against the frozen `GET /v1/me` shape in section 6 and the
`POST /v1/me/exports` contract in section 4.5. `api/**` is the `bnet-api` lane's; every test
here stubs the routes.

## Global Constraints (from spec section 1, plus this lane's file ownership)

- Never persist a Battle.net access token anywhere; the web never sees one at all (out of
  scope here — login is server-side).
- Never log a token, code, or state (not applicable to this lane's files).
- `characters[]` gains `realm?, level?, faction?, source?, guild?`; `Me` gains
  `bnet_imported_at?`. Every new field is optional on the TypeScript side (the "normaliser"
  the spec calls for): there is no runtime schema validation anywhere in `account/api.ts`
  today (`Me`/`MeCharacter` are plain interfaces cast from `envelope.data`), so "treat every
  new field as optional" means the interfaces declare them `?`, matching how `entitlements?`
  already works. No new runtime parsing is introduced.
- Refresh has no new endpoint: it is `battlenetStartUrl('/account?refreshed=1')`, the existing
  route.
- `bnet-web` owns `web/**` and this plan file only. `bnet-api` owns `api/**` and
  `docs/superpowers/plans/2026-09-22-bnet-api.md`. Every test in this lane stubs `/v1/me` and
  `/v1/me/exports` with `page.route`/`vi.stubGlobal`, never waiting on the API lane.
- House rules from `.superpowers/journeys/lane-common-web.md`: functions <50 lines, files
  <800 (Account.svelte stays close to its current size by moving the Characters section out,
  not by growing further), no magic numbers, no dead code, immutable updates, every visible
  string in a copy module, `svelte/server`'s `render()` + `data-testid` substrings for
  component tests (Account.test.ts's convention).

## RULING 1 — the paste box needs a character identity the export string does not carry

The FS1 export string (`FS1_PREFIX`, `web/src/lib/planner/fs1.ts`) encodes data-build, class,
race, talents, gear, bags/bank/sets/loadouts/professions, and (spec's guild-membership design)
a `guild=` section — never a character name, region, or ruleset. Confirmed by reading
`FS1Build` (no such fields) and the wire syntax in
`docs/superpowers/specs/2026-09-21-guild-membership-design.md` §1.2. The companion's own
`POST /v1/addon/exports` payload (`api/internal/addon.Export{Name,Region,Ruleset,Export}`)
supplies those three fields *outside* the export string, because the companion reads them
from the game client directly. `POST /v1/me/exports` (spec 4.5) needs the same three fields
per character, and `AddonPasteBox.svelte` — a bare textarea paste, no companion, no game
client — has no source for them.

**Decision:** `AddonPasteBox.svelte` gains three small fields (character name, region select,
ruleset select) that appear only once a decode has succeeded *and* the viewer is signed in
(`fetchMeOnce`), with an explicit "Save to your account" action gated on all three being
filled — not an automatic POST on decode, since decode alone never has enough information to
build a valid `Export`. Signed out, or before a successful decode, nothing changes.

**Cost if wrong:** guessing at a default (e.g. inferring region from the browser locale) could
silently save a character under the wrong region/ruleset, creating a phantom `characters` row
that then collides with the real character's key on the next Battle.net import or companion
sync (`ON CONFLICT (key) DO UPDATE ... WHERE user_id IS NULL OR user_id = excluded.user_id`
guards against stealing another account's row, but not against a self-inflicted wrong key).
Asking directly costs one extra step and is the only certain source of the right values.

## RULING 2 — `CurrentCharacterBar`'s "current key" is the armory pointer's `ref`

`CurrentCharacter` (`web/src/lib/current-character.ts`) has no `key` field. The one source
kind whose `ref` *is* a `region/ruleset/slug` character key is `'armory'`
(`web/src/components/sim/LandingState.svelte`: `{ source: 'armory', ref: character.key }`).
Spec 7.5's "the `/v1/me` character matching the current key" therefore means: when
`current !== null && current.source === 'armory'`, look up `me.characters.find(c => c.key ===
current.ref)`. Every other source (`addon`, `build`, `fight`, `code`) carries no character key
and shows no guild line — unchanged from today. Cost if wrong: a guessed match (e.g. by label)
could show a stranger's guild on a card containing no server data to verify it against.

4. Add `postMyExports`:
   ```ts
   export interface MyExportInput { name: string; region: string; ruleset: string; export: string }
   export async function postMyExports(
     exports: MyExportInput[],
     apiBase: string = API_BASE_URL,
   ): Promise<MeCharacter[]> {
     const result = await call<{ characters: MeCharacter[] }>('/v1/me/exports', apiBase, {
       method: 'POST',
       body: { exports },
     });
     return result?.characters ?? [];
   }
   ```
   Follows `pairDevice`'s/`setAnonymize`'s existing shape exactly (`call()` already adds the
   CSRF header and credentials for any non-GET); a failure throws `AccountError` with the
   API's own message, same as every other call here.
5. Test: `vi.stubGlobal('fetch', ...)` returning the envelope shape, assert the POST body and
   that a failure surfaces the API's `error.message` (mirrors an existing `setAnonymize`/
   `pairDevice` test in `api.test.ts`).

## Task 2 — `relativeTime` in `dates.ts`

**Files:** `web/src/lib/dates.ts`, `web/src/lib/dates.test.ts`.

Add one pure function, reusing `formatDate` for the fallback bucket:
```ts
const MINUTE = 60_000;
const HOUR = 60 * MINUTE;
const DAY = 24 * HOUR;

/** "3 hours ago", falling back to formatDate past 30 days. Never a negative duration --
 *  a clock skew or a server timestamp a few seconds ahead reads as "just now". */
export function relativeTime(d: Date, now: Date = new Date()): string {
  const elapsed = Math.max(0, now.getTime() - d.getTime());
  if (elapsed < MINUTE) return 'just now';
  if (elapsed < HOUR) {
    const minutes = Math.floor(elapsed / MINUTE);
    return `${minutes} minute${minutes === 1 ? '' : 's'} ago`;
  }
  if (elapsed < DAY) {
    const hours = Math.floor(elapsed / HOUR);
    return `${hours} hour${hours === 1 ? '' : 's'} ago`;
  }
  const days = Math.floor(elapsed / DAY);
  if (days < 30) return `${days} day${days === 1 ? '' : 's'} ago`;
  return formatDate(d);
}
```
Test each bucket boundary (59s, 61s, 59m, 61m, 23h, 25h, 29d, 31d).

Run: `npx vitest run src/lib/dates.test.ts`.
