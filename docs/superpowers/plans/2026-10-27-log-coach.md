# Log Coach Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** After any logged boss pull, a player opens a review from their spec's coach: a mentor in the voice of the best player of that spec on Forever, who writes only from a rule-computed evidence pack. The API checks every number, spell, time, anchor and link in the review against that pack before anything is shown, and falls back to a rule-only rendering when the model fails, is capped or is switched off. Free owners see the count and the first thing to fix. Premium (`log_coach`) sees the whole review on the report page, one line in Discord's `/report`, and one line on the account page.

**Architecture:**
- **Consumables first.** One engine function, `consumables.AtPull`, reads the player's seeded aura tracks against the catalogue. The rating's three readers and the coach's F6 all use it. `ratingengine.DefaultModelVersion` moves, a CLI re-rates and rebuilds the preparation digests, and the catalogue gains `raid_buffs` and a per-category `complete` flag.
- **`api/internal/coach`, the pure core.** `coach.Review(Input) Pack` builds the evidence pack from the fight summary, the roster row, the comparison references and the curated tables. F1–F8 live in one file each. The pack holds findings, strengths, computed links, the "couldn't check" lines, the evidence anchors and the allowed-values set. `RenderRules(pack, drills)` is the rule-only rendering.
- **The basis.** Migration 0055 adds `coach_profiles` (partitioned on `fought_at` like `fight_metrics`, written by the rater inside the rating transaction through a hook), `coach_sim_refs`, `coach_packs`, `coach_reviews`, `coach_review_leases`, `llm_spend`, `coach_account_day` and `coach_review_samples`. The pool query takes one best kill per player, needs at least 20 players, and compares with the median of the top 25, bounded to the content phase.
- **`api/internal/llm`.** A plain `net/http` client for the Vercel AI Gateway's OpenAI-compatible chat completions, with timeouts, retries, usage and the gateway-reported cost captured. The caps and the kill switch sit in `coach/caps.go`.
- **Personas.** `data/curated/coach/<spec>.md`, 28 files (the 28 specs of `data/curated/specs.json`): three full (Fury, Holy priest, Protection warrior), 25 starters from `tools/coach/persona_starter.py`. A loader returns the persona with its content-hash version and drill list. The files ship in the API image under `COACH_DATA_DIR`.
- **Prompt, parser, validator, generator.** The prompt is the shared coach rules, the persona, and the pack as JSON. The output parser and validator (shape, numbers, names, times, links, tone) gate every model answer. One validation retry, then the rule-only rendering. Every generation is stored with model, persona version, pack version, tokens, cost and gateway request id.
- **Surfaces.** API routes for one fight's review, the night line, the account's recent line and the character history. Discord's `/report` gains an ephemeral "what to fix first" line, and the raid-night post gains one sentence that names nobody. The web adds the report page row line and Coach panel and the account "last raid" line. A nightly job samples 20 reviews for the owner. The privacy page names the processors. The plans page shows the coach line last of all.

**Tech Stack:** Go 1.25 (pgx v5, golang-migrate, stdlib `net/http`), the `logs` engine module, Python 3 (the starter generator, run through `uv run --project data`), Astro + Svelte 5, Tailwind, vitest, Playwright + axe.

**Spec:** `docs/superpowers/specs/2026-10-27-log-coach-design.md`, final at `e55fff880`. It is the authority. Every threshold, copy string, code, column, output field name and cap in this plan is copied from it, and each task's tests read the spec where the spec holds the string. The architect's map is `docs/superpowers/specs/2026-10-27-log-coach-feasibility.md`. The pricing page rules are `design/specs/2026-10-27-launch-pricing.md` §B5 and §B8.

## Global Constraints

- **Accuracy rules (spec §20), binding on every task:**
  1. Every number, spell, time and comparison in a review is in the evidence pack, and the validator proves it before the review is shown (§10).
  2. Every pack finding carries at least one evidence anchor, and a test refuses one without.
  3. Every review carries the "Couldn't check" list verbatim. Talents and race are on it in v1.
  4. A finding fires only when the data proves it. Missing proof drops or narrows it, and says so.
  5. Thin basis means no finding: `not enough logs yet`, with the real count.
  6. Rule data, catalogue entries and personas are stamped and reviewed. Known-good fixtures pin the obvious answers (a Fury warrior's Bloodthirst count on a real Forever log, a flask that was there, a death to an avoidable ability), and a change that moves one fails the build until a person explains it (tenet 8).
  7. **Fallback:** a review that fails validation twice is replaced by the rule-only rendering. The player never sees an unvalidated sentence.
  8. **Nightly sample:** 20 reviews generated that day, at random, spread across specs where possible, written to `coach_review_samples` and one structured log entry. A moderator route lists them (`GET /v1/admin/coach/samples?day=`).
  9. **Kill switch:** `COACH_LLM_ENABLED=false` forces the rule-only rendering everywhere at once. Stored model reviews stay in the table but are not served while it is off.
  10. Before the plans page renders the held line, each clause is checked against the shipped coach (Task 39).
- **The model is never called in a test.** Every test that reaches generation uses `llm.Fake`. No test reads `LLM_API_KEY`. Only Task 40's evaluation run, by the controller, calls the gateway.
- **Secrets.** `LLM_API_KEY` comes from Secret Manager (already there as `LLM_API_KEY`, readable by api-runtime). It is never logged, returned, stored in a row or put in an error string. A test captures slog output and asserts the key is absent (Task 20).
- **What leaves our systems.** The evidence pack holds spec, boss, size and the numbers of one fight, and **no character name, account, guild, realm or Battle.net data**. A test asserts the serialised pack carries none of them (Task 14).
- **Healer copy never says "heal more".** It is on the tone list (`tone.go`) and every healer test asserts it is absent from titles, details and the rule-only rendering.
- **Copy.** Strings the spec shows are copied verbatim and pinned by a test that reads the spec (`api/internal/coach/spec_test.go`'s `specQuoted`, and `web/src/test-support/spec-table.ts`'s new `specQuoted`). Strings the spec does not show (a title pattern for a finding the spec has no example of, the singular gap line) are drafted in `copy_drafts.go`. Task 33's experience spec fixes them before any surface ships, and its spec test pins them too. No surface outside the Coach panel speaks as the coach (§16).

The rater writes `coach_profiles` through a hook it declares, `rating.FightHook`, which `coach.ProfileWriter` implements and `api/cmd/api/coach.go` wires. `rating` never imports `coach`.
2. **Level.** The log carries no character level: the advanced block's level is the player's ITEM level. Task 4 fills `RosterRow.ItemLevel` from it when COMBATANT_INFO gave none, and the API's ingest overlays `RosterRow.Level` (the character level) from the site's own `characters.level` (addon import / Battle.net capture), matched by character key; 0 when no character matches. Tasks 10/19 read `Level` for the rank check and the sim band (0 goes to "Couldn't check", §6.1) and `ItemLevel` for gear comparisons. No companion release is needed.
3. **Owner decisions, as ruled by the controller (2026-10-27):**
   - The held Premium line reads "after every logged raid". It already does in `plans-page-copy.ts` and in `design/specs/2026-10-27-launch-pricing.md` B5.
   - The scope note changes when the coach line renders, to the spec's proposal: `Sims cover damage specs; healing and tanking specs are not simulated yet. The coach reviews every spec; damage specs get the most findings.` (Task 39).
   - "Top" for healers and tanks is the rating's overall score (`coach_profiles.metric`).
   - The provider behind the slug must not train on API inputs and must state its retention. `LLM_PROVIDERS` pins the gateway to providers that meet both, even at a higher price. It is required when the coach is enabled (Task 21), and the choice is recorded in the build notes below.

   - Caps: `COACH_DAILY_SPEND_CAP_USD=25`, `COACH_DAILY_REVIEWS_PER_ACCOUNT=30`.
4. **Generation runs on the jobs runner** (`jobs.Runner`, the same `jobs.NewCloudRun` the API already uses for `sim-run`) as the command `coach-review`, in its own Cloud Run job: one `CloudRun` is bound to one job, so each command (`coach-review`, `coach-simref`) gets its own runner. ## Part 1 — Consumables at the pull (spec §13)

### Task 1: `consumables.AtPull`, the raid-buff list and the `complete` flags

**Files:**
- Create: `logs/engine/mechanics/consumables/atpull.go`, `atpull_test.go`; `logs/engine/event/testdata/forever-boss-pull.log` (a real Forever boss pull, cut by the controller from the owner's beta logs in `/Applications/World of Warcraft/_classic_beta_/Logs/`: one pull with COMBATANT_INFO for a player whose flask aura is up at the pull and one whose is not, a Fury warrior, and ideally a death to an avoidable ability; a dungeon boss is fine; if no such pull exists, this task reports BLOCKED); `logs/engine/summary/testdata/forever-boss.summary.json.golden`
- Modify: `logs/engine/mechanics/consumables/consumables.go` (types, `Parse` checks), `catalogue.json` (`raid_buffs`, `complete`), `consumables_test.go`; `logs/engine/summary/golden_test.go` (one `goldenDialects` row for the new excerpt)

**Interfaces:**
- Produces (`consumables`):
  ```go
  const (
      CategoryFlask         = "flask"
      CategoryFood          = "food"
      CategoryWeaponEnchant = "weapon_enchant"
      CategoryWorldBuffs    = "world_buffs"
      CategoryCombatPotion  = "combat_potion"
  )
  // RaidBuff is one raid buff and the class that provides it; SpellIDs is every rank.
  type RaidBuff struct {
      Name     string  `json:"name"`
      Class    string  `json:"class"` // the log's class name, as summary.RosterRow.Class ("Priest")
      SpellIDs []int64 `json:"spell_ids"`
      Verified string  `json:"verified"`
  }
  // RoleCatalogue gains:
  //   Complete map[string]bool `json:"complete"` // category -> the list is complete
  // Catalogue gains:
  //   RaidBuffs []RaidBuff `json:"raid_buffs"`
  func (rc RoleCatalogue) IsComplete(category string) bool
  func (c Catalogue) AllRoles() RoleCatalogue // every role's entries merged, for the discipline readers
  // Pull is what one player brought into the pull, read from the seeded aura tracks.
  type Pull struct {
      Known      bool               // the log has a character sheet (a combatant row with gear) for the player
      Present    map[string][]Entry // category -> catalogue entries seeded on the player at 0 ms
      PotionUses int64              // successful casts of combat_potion entries, owner-folded
  }
  func (p Pull) Has(category string) bool
  func Seeded(fight summary.Summary, guid string, spellID int64) bool // an aura track on guid with a segment starting at 0 ms
  func AtPull(fight summary.Summary, guid string, rc RoleCatalogue) Pull
  type RaidBuffState struct {
      Buff             RaidBuff
      Present          bool // any rank seeded on the player at 0 ms
      ProviderInRoster bool // a roster row of Buff.Class in this fight
  }
  func RaidBuffsAtPull(fight summary.Summary, guid string, buffs []RaidBuff) []RaidBuffState
  ```

- `Review`:
  - Not reviewable (`StatusNotReviewable`): no encounter (trash), under `MinFightMS`, or a row with no spec (`NotReviewableSpec`).
  - `StatusPreparing` while `Refs.SimPreparing` and the sim would be some finding's only basis.
  - Runs the eight checks in a fixed order, keeps one finding per code, ranks major before minor and then by `Precedence[role]`, and caps at `MaxFindings`. Ids `f1…`, `s1…`, `l1…`, `a1…` follow rank order.
  - **Raid buffs are never rank 1.** A preparation finding about raid buffs alone ranks after every other finding. If it is the only finding, ranks start at 2: no finding is rank 1, `RenderRules` has no fix first, and the teaser's `fix_first` is null.
  - `CouldNotCheck` always starts with `CannotTalents` and `CannotRange`, then each check's lines in check order, deduplicated.
  - Strengths: the checks' strengths, ordered by finding precedence.
  - `Context`: spec label, class, role, boss, size, kill, `Clock(duration)` and level. Never a name, account, guild or realm.
  - `BasisLabels`: every basis and comparison label used, deduplicated, for the panel footer.
- `links.go`: `func computeLinks(fs []Finding, windows map[string][]ratingengine.Window) []Link`, the five v1 kinds of §7. A link exists only when the windows or ids actually meet in this fight. Sentences come from `Drafts`, except the §5.3 examples.
- `allowed.go`: `func allowedOf(p Pack) Allowed` holds every number in every finding's, strength's and link's facts as it may appear, normalised (thousands separators removed: `2,140` becomes `2140`; `%` kept as part of the token), every `m:ss` time, every range, the size, level and duration; every spell, item and boss name; every id; the spec and class names of the player. Lookups: `func (a Allowed) HasNumber(norm string) bool`, `HasTime`, `HasRange`, `HasName`, `HasID`.
- `RenderRules`: the opening is `RulesOpening` with the boss, or `RulesNothing` with no findings. Fix first is rank 1, with its detail as the why and `drills["drill."+code]` as the drill. Then fix is ranks 2–4. Doing well is the top two strengths. Couldn't check is copied as is.

- Flow:
  1. `Caps.Admit`. A refusal stores the rule-only rendering with `Reason` the refusal and `Retryable: true`, and calls the model never.
  2. `LLM.Complete` with `BuildPrompt`, `OutputSchema()`, the temperature and 1,200 max tokens. Every call's cost goes through `Caps.RecordSpend`.
  3. `ParseOutput` and `Validate`. A pass stores `source: "model"`.
  4. On failure, one retry with the first two messages plus the model's answer and `RetryMessage(problems)`. A pass stores `source: "model"`.
  5. A second failure stores the rule-only rendering, `source: "rules"`, `Reason: "validation"`, `Retryable: false`, and logs one structured entry with the pack, both outputs and the problems (never the key, never a character name).
  6. A model error (after the client's own retries) stores the rule-only rendering, `Reason: "model_error"`, `Retryable: true`.
- Tokens and cost on the row are the sum over both attempts; `ModelSlug` and `RequestID` are the last attempt's.
