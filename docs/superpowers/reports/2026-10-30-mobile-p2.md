## What was built

1. **Version.**
   - `apps/VERSION` holds `APP_VERSION = 0.1.0` and `APP_BUILD = 1`, in xcconfig syntax.
   - iOS includes it through `apps/ios/Version.xcconfig` (`configFiles` in `project.yml`).
   - Android reads it through a new `forever.app-version` convention plugin, which fails the
     build on a malformed file.
   - Both apps have a test that the built version equals the file.
   - `apps/CHANGELOG.md` holds the notes.
   - `ios.yml` and `android.yml` now also trigger on `apps/VERSION`.
2. **Client identity and forced update.**
   - Both apps send `X-App: ios|android/<version> (<build>)` and `X-App-Install: <uuid>`.
     - iOS: an `IdentifiedTransport` wraps the live or fixture transport.
     - Android: a Ktor plugin.
   - The install id is a random UUID.
     - iOS keeps it in UserDefaults on purpose, because the Keychain survives a reinstall.
     - Android keeps it in `forever_install` prefs, excluded from backup and device transfer.
   - A `426 update_required` answer:
     - becomes `APIError.updateRequired(storeURL:)` on iOS and `ApiError.UpdateRequired` on
       Android;
     - shuts an `UpdateGate` the app root watches.
   - Every screen then gives way to "Update Forever Sixty", with one button to
     `error.fields.store_url`. Only https links are used; otherwise the button opens the
     app's own store page.
   - Goldens were recorded on both platforms, and the button label was checked for contrast.
   - `app-v1.md` documents the headers, the 426 and the new error code.
   - API (dark):
     - `api/internal/appclient` plus `httpx.AddLogAttrs`.
     - The flags: `APP_CLIENT_HEADERS`, `APP_MIN_VERSION_IOS`, `APP_MIN_VERSION_ANDROID`,
       `APP_STORE_URL_IOS` and `APP_STORE_URL_ANDROID` (the last defaults to the Play page).
3. **Crash and hang reporting.**
   - Sentry, through `sentry-cocoa` 9.30.2 and `sentry-android-core` 8.61.0.
   - Pure `Scrubber` and `CrashReportingPolicy` modules with the same rules and tests:
     `Sources/Telemetry` on iOS, `core/telemetry` on Android.
   - Off in debug, in fixture mode and with no DSN. Android auto-init is off.
   - The DSN comes from build config: the `SENTRY_DSN` xcodebuild setting, and
     `SENTRY_DSN_ANDROID` (release only). Both are empty placeholders.
   - `apps/shared/privacy.md` has the App Privacy and Data safety answers, plus the Sentry
     project settings.
4. **Release command.**
   - `tools/release-apps.sh`, or `make -C apps release`. It is a dry run by default.
   - It bumps the version, rolls the changelog, commits, tags (annotated), builds signed,
     uploads to Play internal with fastlane, and uploads to TestFlight. TestFlight is guarded
     until the Apple secrets exist.
   - fastlane 2.241.0 is pinned and locked in `apps/Gemfile`.
   - `apps-release.yml` runs it with workflow_dispatch, using `android.yml`'s existing secret
     names. The old `play-internal` job in `android.yml` is removed, so there is one release
     path.
   - `tools/tests/test_release_apps.sh` (44 assertions, stubbed tools) runs in `tools.yml`.
5. **Runbook.** `docs/runbooks/mobile-apps.md` covers every item in the brief, plus the
   one-time owner setup and how to count app traffic.

## Decisions

- **Sentry, not Crashlytics.**
  - Sentry reports iOS app hangs; Crashlytics does not.
  - Sentry can refuse to store IPs. With `sendDefaultPii` off, both SDKs send `infer_ip: never`.
  - iOS stays free of the Firebase SDK, because its push goes straight to APNs.
  - One vendor can later cover the site and the Go API.
  - Firebase stays on Android for FCM only.
- **Counts go out as log fields, not through a metrics package.** `internal/metrics` is the
  ranking row, not request telemetry. App requests carry `app_*` fields on the existing
  `request` log line, and the runbook creates the `app_requests` and `app_errors` log-based
  metrics with labels. This adds no new dependency and works across Cloud Run instances.
- **The gate compares `x.y.z` only.** It runs after CORS and before auth, so it also blocks
  sign-in. A malformed or missing `X-App` is never an error.
- **One build counter.** `APP_BUILD` is both the iOS build number and the Play versionCode,
  and it rises on every upload. The release commit is pushed even when an upload fails, so a
  spent number is never reused.
- **Platform CLIs build, fastlane uploads.** gradlew and xcodebuild do the builds; fastlane's
  `upload_to_play_store` and `upload_to_testflight` do the uploads. The Play key reaches
  fastlane only through `SUPPLY_JSON_KEY_DATA`, and the .p8 only through a file in a 0700
  temp directory.
- **Sentry keeps its own random install id** as `user.id`, which the crash-free user count
  needs. Every other user field, the server name and the request are dropped. The privacy
  forms declare a "Device ID", not linked to the player.

## Concerns

1. **No Sentry symbol upload yet.**
   - Android traces from R8 builds are unreadable in Sentry without the mapping. It is kept as
     a 90-day workflow artifact and sent to Play.
   - iOS dSYMs go to App Store Connect only.
   - The fix is sentry-cli in the release script, or the Sentry Android Gradle plugin, once the
     projects and an auth token exist.
2. **The iOS release path is untested against Apple.** No account exists yet. The archive and
   export use automatic signing via `-allowProvisioningUpdates` with the App Store Connect key.
   The first real run needs watching.
3. **The workflow pushes to main with `GITHUB_TOKEN`.** That works only while `main` has no
   branch protection blocking Actions. It also runs on macOS for both platforms, at a higher
   minutes cost.
4. **The first Play upload must be manual.** The API cannot create the first release of an
   app.
5. **Apple guideline 5.1.1(v): in-app account deletion.** Battle.net sign-in creates
   accounts, so the app needs a "Delete account" entry, or a link to the request flow, before
   App Review. That belongs to F1. Today deletion is by email request (the privacy page).
6. **`X-App-Install` is logged next to request paths that hold character names.**
   - The privacy forms say "not linked", which is true by policy: it is never joined to an
     account.
   - A strict reading could call it linkable through paths.
   - If that matters, hash the id in the middleware or drop it and count builds only.
7. **Conflict risk with P1.** P1 may also edit:
   - `docs/contracts/app-v1.md` (a short new Conventions section here);
   - `settings.gradle.kts` (one `include` added);
   - `libs.versions.toml` (Sentry and the plugin alias).

   Each change is small and additive.
8. **Local only.** `apps/android/local.properties` was written for the SDK path. It is
   gitignored.
